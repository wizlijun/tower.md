# 经验教训

## 2026-10-18 压缩后从正确的读取入口核验回执

- `Session::events(0)`只返回保留的tail，不能据此断言快照归档中没有原事件；协议`subscribe(0)`在已压缩hub上会返回SnapshotRequired，也不是读取当前head的通用方法。
- 检查已归档回执时先验证实际Git archive，再逐字段比较本地confirmed的完整原Event；比较Hub是否新增事件／租约时，从实际当前contiguous游标订阅并核完整head。先读目标API，不能把压缩前夹具的读取方式直接搬到恢复／压缩后场景。
- 可重跑验证器必须为每次尝试保留独立日志与收据，先检查已有文件再写入；不能复用同名文件覆盖上一次失败。若发生覆盖，只能如实保留工具返回的有限摘录，不能冒称原始完整日志仍在。

## 2026-10-18 避免执行校验积压

- 用户要求“以后避免这个问题”。实际诊断支持短命进程安全校验积压，尚未锁定最初触发程序，不能承诺彻底杜绝或声称重启是唯一解。
- 重型构建、Rust/前端测试和打包由一个负责人统一排队，同一时刻只运行一个批次；Agent可并行读代码，不各自启动重跑。重复使用已构建的同源产物，尽量减少反复启动同名预览和新建验证二进制。
- cargo --version等健康探针启动迟滞时，停止追加新进程；只保留一个必要检查，取消明确属于本任务的过时命令，检查syspolicyd与日志。不得反复启动更多工具“试试看”，不擅自关闭安全服务或移除隔离属性。
- 调试时可限定构建作业/定向测试资源，须如实记录；最终要求的默认并发与性能回归仍按原条件执行一次，不能靠降低并发、放宽时限或删断言掩盖失败。

## 2026-10-18 隔离构建不能共用可变 pnpm 安装目录

- 现象：固定提交工作树用 symlink 复用主树 node_modules／pnpm cache；pnpm 仍会调整模块元数据，后续主树命令触发117个锁定包重新安装，干扰并行前端验证。构建源码虽隔离，依赖目录并非只读。
- 规则：隔离构建使用独立 node_modules 与安装元数据；只复用包管理器允许的内容缓存，或串行完成共享目录的全部操作。源码／锁清单不是完整环境封闭证明；实际安装失败保留日志，不改版本或放宽锁。

## 2026-10-18 私有草稿验收隔离独立快照提交

- 现象：为实际出版B0而释放main后，继续断言后续Create/Edit期间main始终等于B0提交；真实后台快照可以合法追加快层状态，导致链路末尾把快照推进误判为创建草稿改动main。创建、编辑、重开和批准拒绝断言已过，失败日志原样保留。
- 规则：B0出版事实用不可变tag和对应created commit核对；私有草稿“不改main”的阶段显式在自有夹具检出main，再冻结该时刻main/HEAD/index/status作比较。不要关闭真实worker、放宽工作区断言或将合法快照推进归为产品缺陷；测试各阶段按所需权威状态独立建基准。

## 2026-10-18 新 producer 逐栏核对共享事件信封

- 现象：新 baseline review producer 与 ledger 从其他人工动作类推使用 L5，定向测试跟随同样假设通过；真实既有 publication 恢复回归拒绝这份批准。共享证明契约明确规定此事件为 L1。
- 规则：每种新 producer 对照唯一共享表逐栏核 layer、obj、actor、host、guards、eid 与 typed body/receipt；先保留并运行已有消费者回归，不能为迎合新实现改正确旧夹具，也不能接受两个层级绕过冲突。

## 2026-10-18 并行共享文件按冻结补丁暂存

- 现象：注释编辑提交暂存整个baseline_draft.rs时，夹带另一任务刚加入、实现尚未提交的freeze_source导出；暂存stat未暴露此依赖。立即只修索引并重写尚未发布的自有提交，工作区保留对方原行。
- 规则：共享路径暂存后必须逐行核cached diff及导出所依赖文件是否也在本次索引；stat和工作区绿测不证明提交自足。对仍由另一Agent修改的文件使用冻结补丁或精确索引blob，不能直接git add整文件。纠正只动自己的提交/索引，不撤销对方工作区内容。

## 2026-10-18 MVP 必须沿已批准规格裁剪

- 现象：用户要求人/Agent可编辑非树形卡片图后，Agent自行新建text-only画布、独立草稿ref和进程鉴权，用户指出“没有按spec来开发mvp”。
- 规则：先列FR、用户旅程和既有契约，再选最小垂直闭环；减少功能数量不能替换权威数据、草稿、批准、writer或里程碑验收。自由卡片并入同一tower.canvas，不另造便签产品；规格明确后置的安全设计不得成为当前实现前置。原型可见、测试通过、保存重开均不等于spec的MVP完成。

## 2026-10-18 最小完整包含真实输入输出

- 现象：演示画布可见后，用户进一步要求“请实现出来，要求功能最小化完整”。
- 规则：演示用于快速确认方向，下一步必须打通真实输入、可操作结果、刷新、错误与空态；保持范围小，不以更多假数据替代真实接线。原型包与正式发布、测试通过与实机视觉验收分别如实说明。

## 2026-10-18 原型先交付可见竖切片

- 现象：后端整改与完整验收持续推进，但用户仍看不到画布，明确纠正“快点看到原型，不要做太多细节”。
- 规则：原型阶段优先可见、可操作、可自行验证的核心路径；不要让完整后端和发布验收阻塞界面反馈。演示数据与真实状态明确标注，不模拟人工批准或持久化成功。耗时检查可按用户优先级中断，并如实记录未完成。

## 2026-10-18 固定来源归档与嵌套schema先验证

- 现象：来源归档名称漏掉URL中的版本tag，两个版本同名文件冲突；随后又把实际为path/sha256对象的frozen_source_tar当字符串，核验在准备阶段停止。两次错误收据独立保留，没有作PASS。
- 规则：先实际打印所用嵌套字段的类型与键，再处理值；从URL解析并核对tag与相对路径，归档名必须包含二者。下载hash和目标既有字节分别校验，不能用命名冲突推断上游内容不一致。每轮先枚举编号对应的实际receipt basename，禁止从前轮名字或摘要猜测；77的误猜错误已另存，不作产品失败。

## 2026-10-17 整体补丁字节比较先核生成命令

- 现象：Root给冻结补丁校验命令额外加`--full-index`，与作者实际`git diff --binary base tip`的index头缩写不同，整体字节断言失败；源码、Git blobs和归档均一致。
- 规则：先读取产物实际生成命令再做整体字节比较，不为校验擅加改变展示格式的选项。完整blob身份另用实际ls-tree/cat-file逐路径核对；辅助校验错误单列保留，不归为产品失败或改写原封存工件。
- 归档清单比较同样先查看实际首个成员及顶层前缀；不能把归档的 `source/` 前缀当成inventory相对路径，或据此判源码漂移。先核安全路径和成员类型，再按已观察到的唯一前缀映射比较，不物化改写原件。

## 2026-10-17 验证入口与证据结构先实读

- 现象：独立实现/审查反复在启动时找不到Cargo；Root把嵌套base/candidate的source-inventory条目按命令before/after的扁平条目读取，辅助核验发生KeyError，产品尚未运行。
- 规则：本机Cargo直接使用已验证的 `/Users/bruce/.cargo/bin/cargo`，委派时明确传递。每种新证据文件先枚举实际文件名、读取顶层类型/键和首条完整结构，再写核验器；不要根据测试描述猜日志basename，也不要默认JSON顶层一定是对象。source清单与命令收据不能凭相似名称共用字段假设。准备失败单列保留，不计产品红测，也不改原收据。
- 相似的Git reader也先读目标函数：私有引用的find_map会忽略非exact子ref，Catalog权威reader的严格记录校验不同。不能把一个函数的拒绝语义凭印象套到另一个，进而虚构兼容冲突；疑虑先用固定源码确认，再设计负控。

## 2026-10-17 夹具比较真实项目身份

- 现象：新增调度顺序断言将canonical项目路径与未canonical临时路径比较，又将已迁移到linked worktree的展示root与最初root比较，诊断在目标阶段前失败。
- 规则：夹具顺序按实际Project的Arc身份或已核canonical common判定，不能把可迁移展示root当固定身份。先单项确认新增断言可达，再运行默认集合；全fixture Git次数不冒充5秒目标窗口内的调用次数。

## 2026-10-17 生成器与路径校验必须共享实际字符语义

- 现象：扫描器对原字符判断字母数字后转小写，合法 `İ` 展开为 `i` 加组合点；草稿 renderer 再用字母数字白名单检查生成 ID，拒绝自己的正常输出。
- 规则：保留稳定 ID 算法，按真正的安全单文件名组件约束守卫路径，不以第二套字符语义重新解释 ID。回归须从真实已提交目录经过扫描、草稿渲染到实际文件读取，既测组合字符，也保路径穿越等负例。

## 2026-10-17 可重建输入包含历史可用性

- 现象：固定 revision/options 的浅克隆补全历史后，S4 将原4模块合为3，删除派生目录再扫描不能复现原结果。
- 规则：捕获派生计算时同时记录影响语义的历史可用性；重建保持原不可用历史，原可用历史后来缺失则拒绝，不能静默引入后补历史。

## 2026-10-17 先对齐本机归档API

- 现象：独立审查重复尝试本机Python不支持的 `tarfile.extractall(filter=...)`，在产品验证前发生准备失败。
- 规则：本机Python3.9先完整核对成员类型、相对路径、重复和逃逸，再逐普通文件安全物化；不要继续尝试不存在的filter参数。准备失败原样保留，与编译、环境和行为失败分开。

## 2026-10-17 测试屏障不能改变被测时序

- 现象：真实Git屏障包装器在逐参数检查时反复启动`cat`，使夹具到不了目标I/O阶段，先触发原有等待时限；失败清理过早删除临时目录又产生无关cwd错误。
- 规则：先精确匹配目标cwd、Git子命令和参数，再读取一次屏障材料，其他调用直接转发真实Git。必须确认进入目标阶段才把后续失败记为行为红；未到阶段的失败保留并标为夹具失败，不放宽原时限。失败清理也先停止调度、等待全部实际worker，再删除自己创建的目录。
- 缩短屏障暂停区时，原始协议append不等于Session已验证安装；保必要完整sync和来源/输入/CAS证明后才能消费摘要。只移动重复的后续I/O，release后先断言迟尾未重置，再重同步，防后续自愈掩盖错误。

## 2026-10-17 常规界面测试由 Agent 完成

- 现象：候选 App 已能打开，Agent 将按钮、系统文件夹选择和取消流程的常规验证交给用户观察；用户纠正："你能不能自己测试"。
- 规则：常规显示与交互先自行自动化验证，工具故障如实记录并继续排查或推进独立开发，不能把测试工作转交用户，也不能将组件测试或窗口存在冒称实机交互通过。只有产品中的真实人工批准和明确要求的真人验收才交人。界面工具曾忽略超时并长时间挂起时，不让其他实现者依赖 Root 的逐次资源 START；无冲突任务应自主推进，验证资源空闲后继续执行。

## 2026-10-17 规格约定不能由实现计划代替

- 现象：用户要求按 M0 整改文档将已实现部分拉回规格；S5 中自行新增验证命令、替换工作树执行机制及改变证据粒度，造成产品路径与 FR-107、16.1 不一致。
- 规则：实现前逐项核对已批准规格的命令、数据位置、执行环境、证据粒度和里程碑验收。需要改变契约时先列裁决并持久化人的答复，再改规格和代码；不能用“工程选择”或安全加固替代原定产品路径，也不能以测试夹具通过代替 daemon 端到端可达。


## 2026-10-16 需求澄清先查知识库，再问人

- 现象：改规格时，把待定问题直接列成选择题问用户；用户纠正："需求溯源和澄清，可以访问 ~/git/sotvault 中的知识库，并可使用 notemd cli 进行检索和查询"。
- 规则：遇到需求含糊或待定问题，先用 `notemd search --vault ~/git/sotvault "<关键词>"` 检索会议记录、研究和规格原文；有依据就直接定，并在规格里加脚注注明出处。只有知识库里查不到依据、又必须由人拍板的事，才问用户，且一次只问一个。

## 2026-10-18 来源竞争重试保持原身份与期限

- 现象：真实native验收在初始S6提交时，快照在证明两次检查之间推进来源，被既有安全校验拒绝；测试仅识别writer busy而提前失败。
- 规则：先定位精确拒绝阶段，不归因后续尚未执行的功能；只对含当前原UUID的已知来源竞争错误重试同一文件原字节，保留原有期限和成功receipt校验，不接受任意proof/uncertain错误，不放宽产品证明。

## 2026-10-18 先核共享失败契约再迁移旧夹具

- 现象：旧 M0 测试在 Hub.append 返回 Invalid 后要求立即释放租约；新的耐久入口按已批准共享契约第 2 节保留原请求并返回 uncertain。最初只看具体 Hub 的错误实现，误把这一差异当成产品补偿缺陷。
- 规则：先读当前批准契约。进入 Hub 写入边界后的失败不能证明原 intent 已取消；测试迁移要证明完整 pending、无 running 投影、显式协调后的真实原回执、同一 Run 和无第二 grant，不能仅改期望数字。真正 append 前的本地语义拒绝继续验证零副作用。

## 2026-10-18 精确提交树先做独立编译

- 现象：Task 与 Proposal 同改 recovery_git.rs，整文件暂存混入未提交 Proposal consumer，隔离提交树出现缺函数编译失败；工作区的通过不能证明这个提交可独立使用。
- 规则：同文件多任务按功能块暂存，保留其他任务工作区字节；以实际 index 物化源码并编译。记录完整 tree 和逐文件哈希，复用验证时明确证明所有相关输入相等；旧失败收据和原源码树保持独立，不覆盖成 PASS。

## 2026-10-18 消费者实施先满足真实提交前置

- 现象：P3评审候选尚未验证提交时，提前让实现者编写P2 finish消费者草稿；回读P2前置明确要求先核P3实际提交和回归。
- 规则：下游可以只读核接口和计划，开始代码实施前逐项核批准计划的实际提交前置。未满足时保存已写草稿并停止扩范围，待真实新基线后重核再接线；不能用‘最终一起验’代替规定的编译顺序。

## 2026-10-18 读取去重不能新增业务前置

- 现象：合并快照 prepared 与 Session bound 输入的相邻读取时，把完整 records／目录相等用作硬拒绝，导致两个原本分别真实校验的合法来源不能并用。默认 core 的冷启动恢复与 Catalog 次数回归实际失败，错误均为 source identity changed。
- 规则：精确相等只决定能否共用读取；不相等时执行原独立 probe，并保后续实际来源与 CAS。不能为性能优化收紧既有输入契约，也不能修改正确旧夹具来迎合优化。正例与物理来源缺失负例都通过后再收口。

## 2026-10-18 故障后的观察水位不等于实际接受水位

- 现象：确认 fsync 故障后，测试以 Session 的旧 tail 统计租约；后续完整同步补入早已接受的 grant，误报为重新领取。
- 规则：验证“本次没有新增写入”时，在操作前从实际 Hub 捕获 contiguous_seq，再检查该游标后的真实事件。保留原 Run、完整原回执和无新增 lease.granted 断言，不以派生投影的旧水位代替生产者边界。

## 2026-10-18 每次候选续作都重复执行范围隔离

- 规则：同文件多任务隔离须成为冻结器的固定步骤，不能只在首次复制执行。每次覆盖 recovery_git.rs 后都将非本批 publication consumer 恢复为实际 HEAD 函数，再封存哈希；隔离遗漏在检查前拒绝，不能把混合候选当作可提交树。
- 隔离源码借用已固定的 node_modules 时，直接调用匹配锁文件的已安装检查器。pnpm 的依赖状态检查可能试图重新安装；不得对共享依赖目录用 CI 自动确认清空。准备错误保留为准备失败，与产品红测分开。

## 2026-10-18 共享构建目录切换源码须强制重新编译

- 现象：红测候选的旧实现文件时间晚于绿测候选；Cargo 的相对 dep-info 与共享 target 可能让切回较早文件时间的源码复用旧产物，绿测编译仅 0.65 秒且仍出现旧诊断。
- 规则：冻结源码哈希不等于已编译产物来源。切换候选后先刷新实际 Rust 输入的文件时间并记录，强制编译当前字节；不删除依赖缓存，不并发构建。受影响结果先标待复核，不能据此扩大产品错误分类或宣称修复失败／通过。

## 2026-10-18 保留式 GUI 夹具的数据目录必须在工作树之外

- 现象：将原 TempDir 夹具改为保留目录时，把 native App 数据目录放进仓库的 `.release/`；即使被 Git 忽略，它仍处于工作树中，被 daemon Ensure 正确拒绝。
- 规则：QA 仓库、App 数据与 runtime 放到独立的任务临时目录，日志和哈希证据另存仓库忽略目录。生成夹具前核对实际数据目录约束，不放宽产品保护。打包器重做 ad-hoc 签名后，应核验完整可执行内容与签名字段差异，再用包内实际 sidecar 测试。
