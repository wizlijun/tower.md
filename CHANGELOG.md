# Changelog

## Unreleased

- **Upgrade: stop the running daemon after updating.** The daemon API moved to version 14; an older daemon that is still running is reported as unavailable until you run `towermd daemon stop`. Event logs from v0.1.1 and v0.2.0 replay unchanged; runs claimed before this version do not appear in the trust ledger.
- **Upgrade: projects initialized earlier keep their `.towermd/AGENTS.md`.** `towermd init` does not overwrite it. To give agents the new delegation rules (read the card, clarify first, `towermd reply` with `--ref`, `towermd report` with `--answers`, `towermd signal`, `dev finish --claims`, configuration flags on claim, `towermd handled` for prompts, `towermd ask --review` and stopping on a hold), add them by hand and record the edit as a process change.

- The first time you open Tower.md you see an empty canvas and one sentence box, nothing else; it never asks for a project type or scenario. Write what you want to do, pick the folder it belongs to, and the sentence becomes an idea card. Or start from existing material with Open project.
- Ideas are kept apart from commitments. An idea is not in the attention list, cannot be claimed and is never delegated. In the App each idea card has a promote button: as the project's goal (one per project; the delegate then drafts the first version for your approval) or as a task, through the delegate card seeded with the sentence. Promoting is your action and exists only in the App. Ideas on a populated canvas wait in a tray in the corner and add no nodes. When one visit promotes more than 3, the App says how many still have nobody following them up.
- Agents and scripts jot ideas with `towermd idea add <text>` (one line, at most 200 characters, signed `process:towermd-cli`) instead of creating tasks; the claim skill tells agents to do this for anything outside their task. The command line has no promote command.
- Delegate with a card of 5 fixed fields: why, done when, limits, checkpoints and self-check. Only done-when is required; without it the delegate button stays disabled. A checkpoint line may end with `@ 2026-10-25 18:00` to set its time.
- Ask the agent to clarify first. It restates the goal, drafts done-when and asks at most 3 questions with `towermd dev clarify <task> <file>`; the task can be claimed only after you answer and finalize the card in the App.
- Checkpoints with a time become report requests. Agents receive them in `delivered[]` until they answer with `towermd reply <request-id> --state <state> --summary <text> [--next <text>]`; a request left unanswered past its time is recorded as silence (see below). A report never counts as progress.
- The acceptance card lists evidence per done-when criterion, in 3 kinds with their own shape, color and label: check, the delegate's own account, and "I used it", which only you can add. A criterion with no evidence shows as Unproven; you can still confirm in one step, and the unproven criteria are recorded.
- When you confirm, you may write one line on what this changed in your view. It is kept with this delegation; it is never required and never prompted.
- Send work back with a reason. A merged task reopens and the reason goes onto its next card. The App then offers to record the correction as a rule, which appears on every later task of the same work kind.
- The trust ledger has one row per delegate configuration × work kind, summarizing the last 20 delegations: first-pass rate, on-time rate, done-when met, out-of-bounds changes, and the measured time to delivery, in-App review time and send-backs. Review time counts only the App. There is no overall score; weakened commitments count the weakenings that configuration caused, and loops count the times Tower.md found its delegations going in circles. Work kinds default to the module ID and can be renamed or merged. The ledger stays on your machine and in your repository.
- Delegation levels are set per configuration × work kind and otherwise inherit the project level. After a full window the ledger suggests one level up or down; a level never changes automatically. Levels are only recorded for now and do not yet change what an agent may do.
- Spot checks pick completed tasks for your review at every level. The rate falls as results improve but never reaches 0: 5% by default (`spot_check_min` in `config.yaml`, never below 1%). A new configuration starts at 100%.
- When more than 5 items wait for your review (`review_backlog` in `config.yaml`), the first screen shows "N waiting for your review" and the delegate button shows "Review before delegating". The hint takes no attention-list slot and does not block delegating.
- `towermd dev finish --claims <file>` takes the agent's note per criterion, `[{"criterion": 0, "note": "…"}]`. It shows as the delegate's own account and never completes a task by itself.
- `towermd task claim` and `towermd dev clarify` accept `--vendor`, `--model` and `--skills-version` next to `--harness` and `--harness-version`. This self-reported configuration identifies the ledger row; changing any of it starts a fresh row.
- Report progress and raise alerts from any agent or shell script with `towermd report --state <state> --summary <text> [--progress 3/7]` and `towermd signal <kind> --level <log|passive|active|time_sensitive> --title <text>`. Inside a run they default to the run's task and delegate; outside one, name the sender with `--from`. Titles over 30 and summaries over 100 characters are refused (`too_long`), never cut. Repeats of the same kind from the same sender about the same object merge into one entry with a count. `active` and `time_sensitive` signals appear in the attention list as self-reported alerts; a sender clears one by sending it again at a lower level. A report never counts as progress, and `claimed_done` completes nothing.
- `towermd task show` adds `delegation`: the card, the rules recorded for its work kind, past send-back reasons and open report requests. The claim and finish skills and the `.towermd/AGENTS.md` written by `towermd init` tell agents to follow them.
- Object cards on the canvas say who sets them: "set by you" (人定: intents, modules, interfaces, done-when criteria, rules and the like) or "pushed by the delegate" (受托者推进: tasks, runs, evidence and the like), and show the type by its plain name. `towermd show` and the daemon canvas API add `set_by` (`human` or `delegate`) to object cards; layers stay internal and slow-layer protection is unchanged.
- Completion is decided by checks. Every development task carries the built-in check `core.verify` (the module verification `dev finish` runs), so a person can confirm completion in the App only for objects no deterministic check applies to. Declare more checks in `.towermd/gates.yaml` (`gates: { crap: { check: eng.crap } }`, `hard` defaults to true); it is read only from the authoritative trunk and changes only through a proposal. A deterministic signal (`towermd signal <kind> --deterministic`) at `active` or above fails the hard check of the same kind: `dev finish` and `dev trailers` return `gate_failed` and the App shows "check failed" (检查未通过). Signals can block but never pass a check, and an unreadable `gates.yaml` blocks until fixed. Each judgement is recorded as `kind: gate` evidence; `towermd task show` adds `delegation.card.completion` with every check's state.
- Tower.md now notices when a commitment gets weaker and tells you, as a "weakened commitment" (承诺弱化) item near the top of the attention list, signed by Tower.md rather than self-reported. It flags a check dropped from `gates.yaml`, a hard gate made soft or marked `deterministic: false`, a higher `review_backlog` or lower `spot_check_min`, fewer done-when or acceptance criteria, and a verification command removed. It checks submitted and captured proposals, an agent's `dev clarify` draft, and `gates.yaml`/`config.yaml` on the trunk. Rewording and anything it cannot judge are not flagged. Proposal details list the weakenings under "this is a weakening" (这是弱化), and the finalize panel says so when you cut done-when items. Nothing is approved or blocked by the flag. A weakening caused inside a delegation counts toward that configuration's row in the trust ledger.
- Each attention-list item is one line of 6 fixed parts, at most 100 characters: when, which object, what happened, why, the suggestion and what you need to do. The order is now: time-sensitive and protection-related items first, then items waiting on your answer or approval (longest wait first), then the rest by reach. The first screen keeps 3; the rest show as "N more deferred", and the project card on the canvas shows the same single line.
- Opening a project shows a 3-line "since your last visit" summary: what finished, what is stuck and what needs you, with details on demand; the longer you were away, the coarser it gets. The last-visit time stays in the App on this machine, never in the repository or the hub; without one, the summary covers the last 7 days. `passive` signals appear only here, and 3 or more sources on one object merge into one line.
- Ask about any node from its details in the App: a question (why, how) or a report request, with a deadline from 1 hour to 3 days. Asking is your own action and exists only in the App. The daemon picks the recipients: a question goes only to those who declared they can answer for that node (`towermd report --answers`, withdrawn with `--no-answers`); a report request also reaches whoever reported on it and the delegate working on it. A question nobody can answer yet is never dropped: it waits in the attention list as "nobody can answer" (无人可答) until someone declares. Recipients receive it in `delivered[]` and answer with `towermd reply`; an answer to a question must cite its basis with `--ref`, and outside a run `--from` names who answers. The node details show each request's state, and open ones can be withdrawn.
- Tower.md notices silence: a request (including checkpoint report requests) still unanswered past its deadline is recorded once as silence (失联), signed by Tower.md. The first only reaches the "since your last visit" summary; when the previous request on the same object went silent too, it enters the attention list. Earlier "overdue" records replay unchanged and count as silence.
- Tower.md notices work going in circles (兜圈子) from events alone: the same next step reported 3 times in a row, the same check failing 3 times in a row, more than 3 questions in 24 hours, or a delegation running over 3 times the median of finished ones of its work kind. Thresholds live under `stuck:` in `config.yaml` and are read leniently (a typo keeps the default); loosening them is flagged as a weakened commitment. Each finding enters the attention list once and counts toward the configuration's row in the trust ledger; it never pauses or blocks anything.
- Sources that cannot call the command line can send the same envelope to the daemon. Use `POST http://127.0.0.1:<port>/tower` with the `x-towermd-instance` header from `towermd daemon ensure`; the project must be open in the App, and events are signed `process:towermd-http`. Or write one envelope per line into `<runtime dir>/inbox/<project_id>/*.jsonl`. The daemon picks a file up once it has been unchanged for 2 seconds, records each line (signed `process:towermd-file`), deletes the file and writes refused lines with their reasons to `rejected/`. The inbox is outside the repository and nothing from it is written into a working tree. Both entries apply the same checks as `towermd report` and `towermd signal`.
- Extensions declare and never run. A manifest at `.towermd/extensions/<id>/towermd-plugin.yaml` on the authoritative trunk installs an extension; it declares the signal kinds it sends, each with a highest level (`max_level`, default `active`) and whether it may be deterministic. Adding or changing one goes through a proposal, and Tower.md never loads or runs extension code. An extension sends as `pkg:<id>[@version][/part]` and may send only the kinds it declares, up to their level. Nobody else may send a kind an extension owns, and a kind declared twice blocks both extensions. An extension's checks can block a gate but never pass one. `towermd ext ls` and `towermd ext show <id>` list the installed manifests and their problems; the command line has no install or enable command.
- In the App you can mark an `active` or `time_sensitive` signal "got it" (it returns when the sender reports again) or mute it for 7 days (it returns at once if the sender escalates). This is your own action, available only in the App; the command line has no such command.
- The App and the command line help use the first-version names: baseline → version, gate failure → check failed, agent → delegate, main → trunk (主干) in App text, lease → claim on the module, slow layer → what people set, "needs baseline review" → "review against the new version", "needs attention" → "attention list", and "N waiting for your review" → "N to review"; the buttons "submit answer", "send interjection" and "record I used it" become "answer", "interject" and "I used it". Command names, argument names and JSON fields are unchanged; help under `towermd dev` keeps its terms.
- Connect a Note.md vault with `notemd: { vault: <path> }` in `.towermd/config.yaml` on the trunk; without it nothing changes. Once connected, the daemon drops one plain `.md` summary per merged task (`task-<id>-<commit>.md`) and per accepted decision (`decision-<id>.md`) into the vault's capture folder (`<inboxDir>/towermd/`). Each is an OKF document signed `generated.by: process:towermd`, with `sources` pointing to the commit and the Tower.md object. It never writes `.note.md`, adds no links, never touches existing notes or the vault's git, and never rewrites a summary you edited, moved or deleted. Connecting records what already exists without dumping it; only later results are written.
- Proposals can cite Note.md knowledge with an optional `sources` list (`{"okf_id": "kb/raft", "block": "b-1a2b3c"}`, the block from a Note.md citation `((kb/raft.md#b-1a2b3c))`). Once approved, the citations go into the published decision's `sources` and its summary.
- Set how many items the first screen of the attention list shows with `attention: { budget: 1–3 }` in `.towermd/config.yaml` (default 3; larger values stay at 3). The rest wait under "N more deferred", on the canvas project card too; nothing is dropped.
- Each attention item says when it reaches you: ‼ now (time-sensitive), ○ next visit, or ≡ summary (passive reminders, only in "since your last visit"). A time-sensitive item that arrives while the App is open raises one macOS system notification, sent by the App; the daemon never notifies. Items already on screen when you open a project do not notify.
- Focus time: list local windows such as `attention: { focus_time: ["09:00-12:00", "22:00-07:30"] }`. Inside one the attention list says only what must stop you interrupts now; everything else waits for your next visit.
- Approve, answer or confirm right on the attention card. A question shows its options (or a text box) and records the answer for this time only; an answer that touches human-owned content still becomes a pending proposal. A submitted proposal has an Approve button that prepares and checks the publication exactly as the proposal panel does; proposals that lower a commitment are left for the full review. A spot check has Confirm done, which records the unproven criteria as the acceptance card does. All three are your actions, signed `human:local`, offered only in the App, and an uncertain submission is retried unchanged; nothing is ever approved by itself.
- Follow-ups: set yourself up to 5 reminders in the App, each a sentence plus a condition: a time, an object finishing, new activity on an object, or a signal about it. A due follow-up joins the attention list after everything else, waits for your next visit and never notifies; complete it on its card. Adding and completing are your actions, signed `human:local`, offered only in the App.
- Quiet objects: the project or a task with no events for `quiet: { dormant_after: 14 }` days in `.towermd/config.yaml` fades on the canvas and is labelled quiet; its attention items move to the end of "N more deferred". Time-sensitive and protection items are never moved.
- A quiet object resurfaces when a follow-up on it is due, when its review rhythm comes round (`quiet: { check_every: { <id>: <days> } }`), or when a connector such as Note.md reports on it after a quiet spell. It comes back with a "where we left off" card: the last conclusion, what was overturned and what is still open. "Seen it" settles it.
- Several machines can share one project through a hub you deploy yourself. `hub-worker/` is a Cloudflare Worker with one SQLite Durable Object per project; set `hub: { url: ws://… }` in `.towermd/config.yaml` on the trunk. Without it each machine keeps its local hub, and no account or cloud service is needed. The remote hub is the only sequencer: while it is unreachable, ordinary events wait in the local outbox and are resent with their original event ID once it is back, recorded exactly once. Claims, renewals, releases and the trunk lease need the hub and fail clearly when it is away; they never fall back to a local hub. Only the machine holding the trunk lease writes snapshots and slow-layer commits; the others follow. Opening a project needs the hub; the App shows "hub offline" and any warnings in the project status. There is no authentication or encryption yet: use it only on a trusted network, for yourself. Only `ws://` is supported. See the usage guide for deployment.
- Place frames (容器) on the canvas from a template. In the App, open the Frames (容器) tray and pick a template, or drag one onto the canvas. Then name the frame, optionally write a one-line rule for the delegate, choose who moves it forward (set by you, or pushed by the delegate), and place it. Four templates ship with Tower.md: kanban, quadrant, timeline and mind map. A `type: template` extension on the trunk is listed too and replaces a shipped template with the same ID; a template with problems is shown with the reason and cannot be placed. A new frame takes the nearest blank spot, and nothing already on the canvas moves. Only you place, move or resize a frame, and only in the App; the template's definition is frozen into the frame when you place it. A signal sent with `--target` set to a frame's ID shows as a badge on that frame, with shape and text as well as color.
- `towermd template ls` lists the templates with their layout and any problems. `towermd frame show <id>` shows a frame's template, rules, place, cards and waiting items. The command line cannot create, move or resize frames, change their rules or decide waiting items.
- Frames hold cards. When placing a frame, choose free (cards written by you or the delegate), bound (cards follow core objects, and a done state appears only once the object is done) or mixed. In the App, add a card from the frame's header, click a card to change its state or archive it, and change the frame's rule text, per-lane limit and update-until date under Rules.
- Delegates write cards with `towermd frame add/update/move/link/archive`, and propose rule changes with `towermd frame propose <frame> <file>`. Every write is checked against the template and the frame's rules; one that breaks them is refused with the reason and nothing is stored. A compliant write still waits for you when you set the frame (a dashed proposal), when it changes what you set (a suggestion), or when it enters a done state the rules say needs a person (a confirmation); rule changes always wait. Accept or ignore each waiting item in the frame; nothing takes effect by itself. One writer holds a frame at a time (`lease_busy` for others, 60-second lease renewed by each write). Past a lane's limit the write still lands, the writer is told to merge or archive, and later cards fold into "+N" so shown cards never move. Past its update-until date, or once its named object is done, a frame becomes a read-only record.
- Cards inside a frame lay themselves out from the template, and a new card never shifts the ones already shown: lanes keep arrival order, a time axis keeps date order, a mind map grows as a tree with each new card on its own row, and a relation frame adds cards in arrival order with lines between them. Drag a card in the App to pin it where you put it (◆ pinned); layout never moves a pinned card, and clicking the pin lets it go back. Pinning is your action, signed `human:local`, offered only in the App; `towermd frame show` adds `pins`.
- Lines to cards in other frames show only while you hover over or click one end. Changes inside a frame show at most once a second, and cards changed since your last visit get a thin border.
- Turn nodes on the canvas into a frame: click "Pick nodes for a frame" (选中节点转为容器), click the nodes, then choose a template beside the canvas. Core objects follow their phase as bound cards in a template with states; other nodes are copied as your own cards, with the lines between them kept as a tree or as relation lines. The new frame takes the blank spot next to the picked nodes, and the nodes themselves do not move. For a mind map or relation frame, the first layout comes from elkjs and is saved as your pins; elkjs runs only here and never on later updates.
- Scanning a repository now groups files by the imports they actually make, not only by directory. Rust, TypeScript/JavaScript, Svelte, Python and Go imports are read from the scanned commit, without running any tool. The directories are the starting point, so a file without imports stays with its directory, and the same commit always gives the same candidates. Each candidate module's confidence and rationale now come from that evidence. In the candidate view, modules below 60% confidence are drawn dashed and labelled "◌ 置信度 xx% · 低". Dependencies between modules show as "依赖 N 处" lines. Files that fit no module sit in one 未划分区 (unassigned) group. The scan panel lists the coverage recheck: files assigned, module count, verify commands and how many files the imports cover.
- Re-enter a draft from the approved baseline. Choose 从基线进入草稿 (enter a draft from the baseline) in the canvas menu, or run `towermd dev scan start --from-baseline`. The scan of the current commit keeps the approved modules, verify commands and layout instead of clustering again. A new file joins the approved module that owns its directory, and is flagged for review; otherwise it goes to the unassigned group. Once verified, 生成草稿并对比 (create the draft and compare) in the scan panel creates an unreviewed draft signed `towermd/<version>`. A read-only comparison then lists each change against the baseline, with a mark and a label as well as color: added, removed, renamed, moved, files, endpoints, verify commands, content, merged into and split from. It also shows the proposal's impact. `towermd dev draft compare <draft-id>` prints the same comparison. Nothing moves on the canvas. A later baseline is still published only through a proposal: an agent submits it with `towermd propose`, and you approve it under Proposals in the App. A draft started from a baseline that is no longer current is refused, and its comparison says so.
- A prompt now shows one of three states for each run it went to: queued, delivered or handled. A delegate that acted on a prompt it received says so with `towermd handled <prompt-id> [--note <text>]` (signed `process:towermd-cli`; the note is one line of at most 200 characters). It is refused before the prompt reached that run, and repeating it changes nothing. The App's prompt log shows each run's state and note, and the run timeline shows the receipt. Handled is the delegate's own word: it is not progress and approves nothing. The `.towermd/AGENTS.md` that `towermd init` writes tells agents to do this.
- The prompt box takes quick commands: `/pause` and `/resume` pause or resume the whole project, `/report [text]` asks a module or task for a report within 24 hours, `/rule <text> --until <time>` sets a temporary rule, and a line `/assume <assumption>` in an answer records the assumption behind it. Each maps to an action the App already has and works only in the App; start with `//` to send the text as typed. The box lists the commands under a fold.
- Temporary rules carry a scope (the project, a module or a task) and a required expiry of at most 30 days, signed `human:local`. While one is in force, every run in its scope receives it in `delivered[]` on each `towermd` call (`message.kind` `rule`, never acknowledged), and `towermd task show` adds `temp_rules`. It stops applying at its expiry and the daemon then records the expiry. A rule cannot be revoked or extended early. The prompt box lists the rules in force. The `.towermd/AGENTS.md` that `towermd init` writes tells agents to keep them.
- An answer with an assumption reaches the agent with an extra line "(假设：…)"; when it is remembered as a module decision, the assumption becomes the decision's `rationale` and travels with every automatic reuse.
- Waive a blocking gate for a while. In the App's delegation details, a declared hard gate that holds the object back offers "豁免…": write a one-line reason and pick how many days (7 by default, at most 30). The waiver is signed `human:local`, covers that one gate on that one object, and cannot be granted from the command line. While it applies the gate reads "waived" and `dev finish`, `dev trailers` and confirming completion pass it; gate evidence lists the waiver's ID first. It lapses at its expiry with nothing to do, and the gate blocks again; it is never extended, and a new one can be granted only after it lapsed. The kit's own `core.verify`, soft gates and broken declarations cannot be waived. A waiver in its last 24 hours appears in the attention list.
- A commit on main that changed only process configuration (`gates.yaml`, `config.yaml` or `.towermd/extensions/`) is now called a minor change in the attention list, and its alert carries `class: minor`. It still blocks until you register it through "convert to proposal".
- Place frames (容器) on the canvas from a template. In the App, open the Frames (容器) tray and pick a template, or drag one onto the canvas. Then name the frame, optionally write a one-line rule for the delegate, choose who moves it forward (set by you, or pushed by the delegate), and place it. Four templates ship with Tower.md: kanban, quadrant, timeline and mind map. A `type: template` extension on the trunk is listed too and replaces a shipped template with the same ID; a template with problems is shown with the reason and cannot be placed. A new frame takes the nearest blank spot, and nothing already on the canvas moves. Only you place, move or resize a frame, and only in the App; the template's definition is frozen into the frame when you place it. A signal sent with `--target` set to a frame's ID shows as a badge on that frame, with shape and text as well as color. Frames hold no cards yet; binding cards to them comes later.
- `towermd template ls` lists the templates with their layout and any problems. `towermd frame show <id>` shows a frame's template, rules and place. The command line cannot create, move or resize frames.
- `towermd dev finish --report <file>` takes the agent's run report: status (`done`, `blocked`, `needs_input`, `needs_decision`, `failed`), a summary of at most 300 characters, checkpoint commits, changed paths, questions, a suspected error class and a proposal. Like `--claims` it is recorded as the delegate's own account and never moves the task; a malformed report is refused.
- Groundwork for headless runs (M3), not yet started by anything: adapters for Claude Code, Codex, Cursor and Gemini, and a runner that starts one, keeps its raw output on this machine under `<git common dir>/towermd/runs/<run>/`, and stops it with SIGINT, then SIGTERM after 60 seconds. Only what the runner observes moves a task: a failed run makes the task "run failed" (releasing the run makes it ready again); a crash or a third failure holds it with an "error" (错误) item in the attention list. Hitting the budget holds it with a "budget" (预算) item. A cost the harness did not report is recorded as unknown, never as 0, and a budget with an unknown cost asks you instead of letting the run through.
- Tasks now stop and wait for you. A task is held when the same run fails verification 3 times in a row (the builtin `core.verify` or a declared hard check), when the path guard stops an out-of-scope change at `dev finish`, or when a run errors or reaches its budget; the attention list shows the matching item. In the App's task details choose: let the agent fix it again, rewrite the task, reassign it, or waive the declared check (7 days by default, at most 30). There is no "pass" choice: a hold never times out into approval and deciding it does not complete the task. Failed verifications and failed runs are counted separately.
- When a claim finds the delegate card without allowed paths, acceptance or a decision it cites on main, the delegate gets `gate_failed` and the task's creator is asked at the same time; the attention list shows "card missing information, task not dispatched" until you finalize the card.
- Delegates ask for your review with `towermd ask "<summary>" --review plan|code [--artifact <path>]` and wait with `towermd wait <V-…>` (exit 5 while it is still open). The plan review (G1) applies before `dev finish`; the code review (G4) binds the code version of the latest passed finish and applies before `dev trailers`; modules marked `risk: high` need both. The task is held while a review is open; in the App you pass it, request changes or reject it, the last two with a comment. A review never passes on a timeout.

## v0.2.0 — 2026-10-22

- Ship an unsigned macOS Apple Silicon preview of the core/development kit split and the C0 command line. The command line changes below are breaking. Harness live acceptance was not repeated for this version; Intel runtime, quantitative NFR-03 performance and the designated Note.md M0 acceptance remain unverified.

- **Breaking: the command line was reorganized and the old command names are gone.** Development kit commands moved under `towermd dev`: `baseline scan` → `dev scan start`, `baseline scan --wait <ID>` → `dev scan wait <ID>`, `baseline show <scan ID>` → `dev scan show <scan ID>`, `baseline show <d-draft ID>` → `dev draft show <d-draft ID>`, `baseline cancel` → `dev scan cancel`, `baseline template` → `dev draft template`, `baseline submit` → `dev draft submit`, `baseline list` → `dev draft ls`, `baseline schema` → `schema dev.draft.submit` (read `data.input`), `check` → `dev check`, `finish` → `dev finish`, `trailers` → `dev trailers`. Also `project view` → `show`, `pause --all` → `pause all`, `resume --all` → `resume all`, `ask --wait <ID>` → `wait <ID>`, and `answer` now requires `--relayed`. Input files stay positional; `-` reads standard input. Old names fail with a usage error.
- **Breaking: restart the daemon and rebuild the App after updating.** The daemon API moved to version 7; an older daemon that is still running is reported as unavailable, without a retry, until you run `towermd daemon stop`. The App now reads the new output of `towermd daemon ensure`.
- **Breaking: update `.towermd/AGENTS.md` by hand in projects initialized with v0.1.1.** It keeps the old command names and `towermd init` does not overwrite it. Change `towermd finish` to `towermd dev finish` and `towermd trailers` to `towermd --text dev trailers` (in text mode stdout holds only the five trailer lines), and record the edit as a process change.
- **Breaking: every command prints exactly one JSON envelope** when stdout is not a terminal: `v`, `ok`, `data` or `error`, `delivered`, `next`, `warnings`. Answers and interjections now arrive in `delivered` instead of being printed ahead of the result. `--json` and `--text` choose the format explicitly; in text mode `--quiet` prints only messages and errors. The text output of `dev trailers` and `dev draft template` holds only the raw content, and messages go to stderr.
- **Breaking: exit codes now tell callers what to do:** 0 ok, 1 internal, 2 usage, 3 not found or not initialized, 4 conflict, busy lease or stale epoch, 5 no result yet (if there is a `next`, wait again as it says; without one (`deferred`) end the turn instead of busy-waiting), 6 blocked by a guard or gate, needs a proposal, or rejected, 7 needs a person, 8 daemon or hub unavailable.
- **Breaking: `ask` and `wait` exit with 5 while the question is still pending or deferred**; only an answer exits with 0. A pending question offers `towermd wait <hold>` as `next`; a deferred one (deadline passed, parked, or an answer awaiting approval of its proposal) offers no `next`: end the turn, and the answer arrives in `delivered` of a later call. An unknown answer status from the daemon is reported as `internal`. `ask --parked` exits with 0 once the question is recorded. `dev scan wait` and `dev finish --wait` also exit with 5 while the work still runs, and a failed or interrupted verification exits with 6 (`gate_failed`).
- Errors carry a stable code. Rejections the daemon does not classify further report the new code `rejected`; a paused project reports `conflict`, a busy or expired lease reports `lease_busy`, and `task add` or `task claim` without an approved baseline reports `gate_failed`.
- Every write accepts the global `--request-id` (UUID v7); a failed write echoes it in `error.retry`. Only transient failures (pending, busy lease, daemon or hub unavailable) are marked `safe: true` and can be repeated unchanged with the same ID; deterministic failures such as `gate_failed`, `conflict` or `rejected` are marked `safe: false`. Scan start, snapshot and hub rebuild requests honor it too.
- `towermd schema [COMMAND]` prints the JSON Schema of each command's output. `towermd help <command>` and `--help` show examples and the exit code table.
- Help and locally generated messages follow `--lang`, `TOWERMD_LANG`, `LC_ALL`, `LANG` or the macOS language, in that order (English by default). Messages from the daemon are still in Chinese.
- Lease and actor messages use the new general names: "project pause forbids new module leases" now reads "project pause forbids new work leases"; "项目已暂停，新任务领取和模块租约申请被拒绝" now reads "项目已暂停，新任务领取和工作租约申请被拒绝"; "模块租约只接受非空 module:<id> 名称" now reads "工作租约只接受非空 <kind>:<id> 名称"; "模块租约 TTL…" now reads "工作租约 TTL…"; the self-reported source check says "自述来源名称/版本" instead of "harness 名称/版本"; and the actor format reads `<producer>/<version>` instead of `<harness>/<version>`.
