# Tower.md v0.1.1 使用说明

本文是 v0.1.1 预览版（M1）的使用说明，原为仓库首页。项目远景见 [README](../README.md)。命令行已按[命令行规格](specs/2026-10-21-spec-towermd-cli.md) C0 重构，本文的命令名已随之更新；其余内容描述的仍是 v0.1.1 的画布与流程。

## 当前可用范围

当前源码提供**画布、冷启动审阅与批准、任务执行证据和人工放行的最小框架**。默认主界面只有画布，详情与操作按需打开。模块结构来自已提交的 JSON Canvas 与对象；任务、问题、禁止和检查未通过通过本机 WebSocket 更新，快层变化不移动节点。

App 通过随包 CLI 连接本用户唯一的本机守护进程。扫描与验证使用公共 Git 目录中的缓存和独立工作树，不改用户工作树或暂存区；基线经 App 明确批准后，才由守护进程出版到 main 和 Git 标签。初始化使用 CLI，Claude Code/Codex 等会话由用户自行启动，Tower.md 提供技能与命令协作。

上述 M1 主路径已完成真实 App 验收：Claude Code 与 Codex 在三个工作树完成十项任务，另验证了 B1 批准、旧任务复核、主干处置、Hub 恢复及恢复后重新领取并完成任务。详见[验收报告](qa/2026-10-21-m1-live-acceptance.md)。本次为 **macOS Apple Silicon 最小预览**，无发行者签名或公证；Intel 运行、NFR-03 定量性能和指定 Note.md 仓库的 M0 验收尚未完成，M2/M3 不在本次范围。

### 先看功能框架

从 [0.2.0 预览发行页](https://github.com/wizlijun/tower.md/releases/tag/v0.2.0) 下载 Apple Silicon ZIP，解压后打开 `Tower.md.app`，也可将它移入“应用程序”。本机只需启动一份 App；随包 CLI 位于 `Tower.md.app/Contents/MacOS/towermd`。真实项目需要本机 Git，以及项目验证命令所需的 Node.js、Rust 等工具。

打开 App，选择“打开功能示例”，无需选择仓库。示例用最简单的模块、版本、任务、提问、验证和放行组件串起流程：点击卡片打开操作，确认示例版本、领取任务、回答问题、选择模拟验证结果，最后放行或退回。

示例状态只保存在当前窗口的内存中，不启动受托者、不运行命令、不写 Git。示例画布明确标注“示例数据”；模拟通过或放行不代表真实证据、版本批准或任务合并。具体展示与流程可在试用组件后调整。真实仓库功能仍通过“打开项目”使用。

## 启动与构建

macOS 开发环境需要 Git、Rust stable、Xcode Command Line Tools、Node.js，以及 `package.json` 固定的 pnpm 11.7.0。在本仓库根目录运行：

```sh
pnpm install
pnpm app:dev
```

`app:dev` 会先编译随包 CLI，再启动 Vite 与桌面窗口。原生目录选择需要桌面 App；单独运行 `pnpm dev` 的浏览器页面不具备本机项目读取能力。

构建可独立打开的 App：

```sh
pnpm app:build
```

默认生成 `src-tauri/target/release/bundle/macos/Tower.md.app`。若设置了 `CARGO_TARGET_DIR` 或 Cargo 的目标输出目录，产物位于对应目录的 `release/bundle/macos/`。此构建不要求发行者签名或公证；macOS 工具链可能生成临时 ad-hoc 签名。

### 第一次打开：从一句话开始

还没有打开项目，或打开的项目画布上还没有节点时，App 只显示一张空画布和一句话输入框，不问项目类型、使用场景或模板。

1. **从一句话开始**：在输入框写下想做的事，例如“做一个把会议录音转成待办的命令行工具”，点“记下”。还没有打开项目时，App 先请你选择这件事所属的文件夹，然后把这句话记成一张“想法 · 未立项”卡片。所选文件夹还不是 Tower.md 项目时，这句话会留在输入框里；先在终端运行 `towermd init`（见下文“CLI 入口”）再打开。取消选择文件夹也会保留这句话。
2. **从已有材料开始**：点“打开项目”（`Cmd/Ctrl+O`），选择已有仓库，之后按下文扫描、审阅和批准。

想法和承诺分开：想法不进关注清单，不能领取，也不会派给受托者。每张想法卡有两个立项按钮，立项是你本人的动作，只能在 App 中做：

- **立项：作为项目目标**：这句话成为项目的目标，每个项目只有一个。目标不会直接改动人定的内容；接下来由受托者起草第一个版本，经你在 App 中批准后生效。
- **立项：作为任务…**：打开委托卡，标题预填这句话，按已批准版本的模块填写范围和完成标准后点“委托”，想法和任务在同一个事件里落定。没有已批准的版本时，只能先立为项目目标。

立为项目目标之后（或直接从一句话开始），让会话中的 Agent 按技能 `towermd-seed` 生长第一个版本：它先运行 `towermd dev seed "<一句话>"`（省略这句话时用已立项的目标）取得草稿意图 I-1 与骨架上限，最多问 3 个问题，写 1–3 个模块的最小骨架和一条冒烟测试，扫描后提交草稿基线；你在 App 审阅并批准 B0，之后它添加不超过 7 个任务，第一个是“空骨架能构建并通过一条冒烟测试”。`dev seed` 只读；项目已有批准版本时返回 `needs_proposal`，此后的生长走提案。目录还不是 Git 仓库时，Agent 先在其中运行 `git init` 再 `towermd init`。

画布上已有节点时，想法收在左下角的“想法”栏里，点开才显示，不增加也不移动画布节点。一次查看中立项超过 3 个时，想法栏提示“另有 N 个已立项的事还没有人跟进”。Agent 和脚本用 `towermd idea add <文本>` 记下想法（见下文“CLI 入口”）。

## 如何查看项目

1. 打开 App，点击“打开项目”，或按 `Cmd+O`（其他平台为 `Ctrl+O`），选择 Git 仓库。取消选择会保留当前项目。
2. 已配置且提交了 `tower.canvas` 的项目会显示节点与关系；拖动空白处平移，滚轮或触控板捏合缩放。
3. 点击节点查看原文，按 `Esc` 关闭详情。空白处右键打开菜单，可刷新、适应画布、查看项目态势或切换项目；键盘也可用 `Shift+F10` 打开菜单。
4. “项目态势”显示读取来源、完整提交号、文档目录和读取诊断。已提交但未出现在画布上的 Module，可从“未摆放模块”查看。
5. 任务等快层状态自动更新；断线期间保留上次画布并在详情提示重连。需要重新读取仓库画布时，使用右键“刷新”或 `Cmd/Ctrl+R`。
6. **不打扰的刷新（FR-50）。**卡片上的任务角标、项目卡的关注计数和休眠标记在 1 秒内的多次变化合并为一次显示，以最新状态为准；切换版本、草稿或项目时立即显示。快层变化只改颜色和角标，从不移动节点。
7. **拟议与关系（FR-45、FR-36）。**待审阅或待补全的提案要改的模块和接口，卡片描虚线边框，标“┄ 拟议 · 提案待审阅”或“┄ 拟议 · 提案待补全”；合并、拆分和改接口的提案，把它关联的模块都套上双线外框，标“⇄ 关系一端 · 另一端 ……”。提案批准后虚线消失、卡片转为实线；驳回或被取代的提案不画标记。标记只读提案投影，不写任何东西，也不移动节点。
8. **新版本与幽灵层（FR-46）。**新版本改变了布局时，卡片约半秒内滑到新位置（系统开启“减少动态效果”时直接到位），画布顶部出现“◌ 旧版本幽灵层（N）”。点开后，旧版本里被删除、移动或改了大小的卡片以灰色点线淡影留在原位，标“◌ 旧版本 · 已删除”或“◌ 旧版本 · 原位置”；再点一次收起。拖动卡片、快层更新、刷新或适应画布都不触发过渡。幽灵层不含分区容器。

### 从源码生成候选画布

已配置的项目可在空画布或右键菜单点击“扫描并验证”。目录扫描完成后先显示候选模块图，验证完成后更新卡片状态，保持节点位置和视口。点击卡片查看实际结果与 Module 原文，右键“扫描说明”查看覆盖率、固定提交、历史共同修改关系、命令退出码和日志摘要。关系线表示共同修改，不代表已确认的接口。

扫描实现 spec 的 S1–S5 冷启动切片。S2 从固定提交逐行读出 Rust（`use`、`mod`、`crate::`/`super::`/`self::` 与工作区内的 crate 名）、TypeScript/JavaScript 与 Svelte（相对路径的 `import`、`export … from`、`require`、`import()`）、Python（`import`、`from … import`，含相对导入）和 Go（按 `go.mod` 解析包路径）的 import，只有指向仓库内已跟踪源码的才算依赖，外部包和解析不了的只计数。S3 以目录分组为初始划分，跑确定性的 Louvain 聚类：同一提交总得到同样的候选，没有 import 的文件留在原目录。模块置信度按模块内与跨模块依赖的比例和依赖密度给出，低于 60% 的在候选画布上画虚线并标“◌ 置信度 xx% · 低”；归不进模块的文件收在“未划分区”。扫描说明另列 8.2 复检：源码分配 ≥95%、模块数 3–9、每个模块有验证命令或补测建议，以及 import 证据覆盖。模块划分仍可经下面的 S6 综合补充语义，再交人审阅；只有完成审阅并在 App 明确批准后才出版 B0，扫描本身不批准。卡片分别显示通过、失败、无测试、超时、取消或未运行；“无测试”表示未发现可执行的验证命令，并附补测建议，不是验证通过。

右键“返回当前画布”可回到 main。“刷新”也会返回 main；原候选仍固定于旧提交，只有再次扫描才会生成新候选。刷新、切换项目或关闭窗口不取消后台任务；需要停止时选择“取消本次验证”，并等待清理结果。刷新后可从菜单恢复进度跟踪。

验证在 `<git-common-dir>/towermd/verify/<scan-id>/worktree` 的分离工作树运行，结束后删除该工作树。执行继承启动 daemon 时的环境，允许网络，不自动安装依赖；分离工作树不是安全沙箱，命令使用当前用户权限。通过 CLI 启动 daemon 时可显式传入所需 PATH、工具链和凭据；App 沿用已经启动的服务环境。

同一 daemon 同时只运行一批验证，同一命令由关联模块共享、只执行一次。默认每条命令最多 2 分钟，整批最多 10 分钟；超时或取消回收整个进程组。报告绑定 commit/tree，包含 `process:towermd-verifier` 署名。命令改变已跟踪源码、HEAD 或 index，以及无法确认清理完成时，均不能报告通过。

报告与 Module 文件位于 `<git-common-dir>/towermd/drafts/<scan-id>/`；日志位于 `towermd/verify/<scan-id>/logs/`，相对公共 Git 目录。每条日志最多保留 1 MiB，界面最多显示开头 4 KiB，并明确标识存储截断；报告不枚举环境变量，命令输出会进入本机日志。重启可读取完成报告，日志缺失或摘要改变时拒绝沿用。删除缓存后须重新扫描并实际执行，不能恢复原来的执行证据。daemon 意外退出时，独立 worker 通过管道关闭请求取消并清理；未完成的扫描重启后显示中断，不自动重跑或变为通过。

退出服务可运行 `towermd daemon stop`，它会先取消活动验证。升级后若发现旧版服务，会明确提示先停止旧服务再重试，不自动启动第二个 daemon。

### Agent 综合 → 持久草稿

S5 完成后，让现有 harness 会话中的 Agent 使用仓库的 [towermd-baseline 技能](../skills/towermd-baseline/SKILL.md)，只读固定提交的源码与文档，进行一次综合。Tower.md 不要求云账号，不代为启动模型或修改全局 harness 配置。技能目录可由用户按自己的 harness 安装方式加载，也可以在会话中明确让 Agent 读取该文件。

在项目目录使用同一 `towermd`：

```sh
towermd schema dev.draft.submit
towermd --text dev draft template <扫描ID> > /tmp/baseline-input.json
# Agent 根据固定提交与 S1–S5 报告编辑临时 JSON，然后提交：
towermd dev draft submit /tmp/baseline-input.json --producer <harness/version>
towermd dev draft ls
towermd dev draft show <返回的d-草稿ID>
```

提交使用已保留的 JSON Schema；模块名称、职责和置信度可综合，意图、接口、验收、风险及问题可补充。当前 S6 保留扫描中的模块 ID、路径和验证命令；合并拆分留 S7。提交者是自报来源，不能产生人类批准；通过/失败只继承原 S5 结果，不能用 Agent 自述覆盖。

守护进程通过临时 index 创建 `refs/towermd/drafts/<id>` 私有提交，保存精确输入、扫描原件与草稿对象/画布；相同输入和 producer 幂等返回同一草稿。用户工作树、index 和 main 均不变。有 origin 时仅推送这个私有引用；推送失败会报错并保留本地原件，可用相同输入重试。读取列表不会访问网络。跨机器发现与获取草稿引用暂未接入 App。

在画布右键菜单选择“查看综合草稿”，打开对应条目。草稿仍位于同一画布，点击卡片看原文，按需查看综合说明。接口关系与历史共同修改分别标注；候选不是已批准结构。来源 main 改变后显示过期；本机验证日志丢失后原文仍可恢复，但明确显示证据不可复核，不显示可信通过。删除 S1–S5 派生草稿缓存不影响已提交的 S6 原件。

### 人在画布审阅草稿

打开综合草稿后，点击卡片，在详情里选择编辑。可改名、合并模块、选择一部分真实源码文件拆分、补充或删除接口、确认/修改验证命令。拖动卡片顶部手柄保存位置；模块边界和命令有变化时，相关模块显示“待重新验证”，原 S5 报告仅作历史证据。确认命令本身不会执行命令，也不会批准结构。

把当前项目已有的 Markdown 文件拖进画布，或在右键菜单输入项目相对路径，确认后形成引用节点。正文来自草稿绑定的固定提交；未提交的文件、外部文件或与草稿对象输出路径冲突的引用会被拒绝。

每次保存生成新的不可变私有草稿引用，保留原综合输入和人工动作，使用 `human:local` 标记本机 App 审阅。草稿列表仍可打开旧修订；删除缓存并重启服务后可重放恢复。保存或推送结果未确认时，界面保留原请求供重试，在确认之前阻止新的编辑与项目切换；重试不会重复创建修订。CLI 没有人工审阅或批准命令。

审阅后在“综合说明”选择“重新验证当前草稿”。检查真实结果，再点“准备批准”，核对冻结内容后点“批准 B0”。成功回执包含实际提交、标签和快照；结果不确定时使用“重试原批准”，不要创建另一个批准请求。草稿保存本身不会写 main，明确批准才触发出版。

### 从已批准基线进入草稿（J4）

B0 出版后，要再调整结构，就从当前已批准的基线进入草稿，而不是从头冷启动。在画布右键菜单选“从基线进入草稿”，或：

```sh
towermd dev scan start --from-baseline
towermd dev scan wait <扫描ID>
```

这次扫描当前权威提交，但沿用已批准的模块 ID、路径、验证命令和画布位置，不重新聚类；S5 只运行已批准的命令。新出现的文件归入同一目录下已批准路径最多的模块，并在诊断里标出待审阅；没有对应模块的进“未划分区”。尚无已批准基线时直接拒绝。

验证完成后，在扫描说明里点“生成草稿并对比”（守护进程接口 `POST /projects/{h}/scans/{id}/draft`）。守护进程把扫描和已批准对象合成一份未审阅的草稿，署名 `towermd/<版本>`，同一扫描重复生成得到同一份草稿。已批准对象原文保留，只去掉批准字段；验收里引用的验证命令不再属于该模块时去掉，并记为风险。草稿的来源基线不是当前基线、或扫描已过期时拒绝生成。

随后照常在画布上审阅草稿：改名、合并、拆分、改接口和验收。右键“与 towermd/B<N> 对比”或在“综合说明”里打开对比，`towermd dev draft compare <草稿ID>` 输出同样内容。对比只读，逐个对象列出变化：新增、删除、改名（附原名）、移动、文件（列出增减）、端点、验证命令、内容、合并入、拆分自，每种都有符号和文字；另列未变化的对象数、未划分区，以及提案将带的影响范围。对比不改变画布上任何节点的位置。草稿的来源基线已被更新的基线取代时，对比照常显示，并提示重新从基线进入草稿。

对比打开时，画布按结构图显示草稿（FR-35）：有变化的对象描虚线，标“┄ 拟议 · ”加变化种类（例如“✎ 改名 · ▤ 文件”）；合并入与拆分自的两个模块、端点变了的接口两端（含原来的端点）套上双线外框并写出另一端；已批准版本里被删除或位置、大小变了的卡片以幽灵层留在原处，默认显示，可点顶部“◌ 旧版本幽灵层”收起。被删除的对象只出现在幽灵层。在“提案”里点“在画布上审阅草稿”时，从基线进入的草稿会同时打开对比。编辑草稿会生成新修订，画布上的对比标记随之收起，重新打开对比即可再看。

出版只走提案：从基线进入的草稿在“综合说明”里不提供“准备批准”。由 Agent 按 [towermd-propose 技能](../skills/towermd-propose/SKILL.md) 用 `towermd propose <input.json>` 提交（对比面板给出可参考的输入），再由你在“提案”中查看差异与影响、明确批准，出版 B1、B2……。命令行不提供批准命令。

### 批准后：任务与 Agent 协作

1. 在画布右键选择“创建任务”，按已批准模块填写目标、允许路径和验收条件；也可让 Agent 用 `towermd task add <json>` 创建任务。
2. 在独立工作树的 `t/<task-id>` 分支启动自己的 Claude Code 或 Codex 会话，让它读取 [领取技能](../skills/towermd-claim/SKILL.md) 与 [收尾技能](../skills/towermd-finish/SKILL.md)，按技能领取任务、提交代码、运行 `dev check` / `dev finish`。App 不代为启动 harness。
3. 在模块卡片或右键“任务与运行”查看真实任务状态、依赖与运行证据。Agent 用 `ask` 提问后，在 App 回答；若人在 harness 会话中已直接回答，可由 Agent 用 `towermd answer <hold-id> "人的实际回答" --relayed` 转述，仅解开当前普通问题，不形成决策、规则或慢层批准。“向项目插话”或任务详情的插话会在 Agent 下次调用 CLI 时送达。插话记录按收件运行显示三种状态：排队中（还没送出）、已送达（已写进 Agent 某次调用的输出）、已处理（Agent 用 `towermd handled <插话ID> --note <做了什么>` 确认办完）。已处理是 Agent 的自述，不算进度，也不批准任何事；插话没送达该运行时，Agent 无法确认已处理。

   插话框接受快捷命令，每条都对应 App 里已有的一个动作，不增加新的权力；以 `//` 开头则原样发送：

   | 命令 | 在哪里用 | 做什么 |
   | --- | --- | --- |
   | `/pause` | 向项目插话 | 暂停整个项目，同“暂停全部” |
   | `/resume` | 向项目插话 | 确认恢复当前暂停，同“确认恢复领取” |
   | `/report [内容]` | 向模块或任务插话 | 请它 24 小时内汇报进展，同节点详情的“要求汇报” |
   | `/rule <内容> --until <时间>` | 任一插话框 | 设临时规则，时间写 `30m`、`2h`、`3d`、`18:00`（下一次到点）或 `2026-10-25 18:00`，最长 30 天 |
   | `/assume <假设>` | 回答问题 | 单独写一行，回答与所依据的假设一起送给 Agent；记为模块决策时假设成为决策的理由 |

   临时规则只能在 App 中设，署名 `human:local`，必须带范围（整个项目、模块或任务）和到期时间。生效期间，范围内的每个运行每次调用 CLI 都会在 `delivered[]` 中收到它，`towermd task show` 也在 `temp_rules` 中列出；到点即失效，随后由守护进程补记一条到期记录。临时规则不能提前撤销或续期，到期后需要时重新设一条。它只是提示 Agent 的做法，不改变任务卡的边界、检查或任何人定内容。插话框上方列出覆盖这个范围的生效规则。
4. 只有 `dev finish` 实际通过后，Agent 才能取得 `dev trailers`，按技能将五项原值写入提交说明并遵循项目 Git 合并流程。只有 daemon 核实权威 main 后显示的 `merged` 才算完成。
5. 需要改变模块等慢层结构时，让 Agent 读取 [提案技能](../skills/towermd-propose/SKILL.md)。在 App 的“提案”中审阅差异、影响对象并批准或驳回；已有任务的复核标记不会因为 Agent 自述而消失。

“暂停全部”会拒绝新的领取，并向既有运行发送检查点指令；它不直接停止 harness 进程。解除暂停须在 App 选择“确认恢复领取”；CLI 的 `resume` 只发请求。

Hub 丢失时，可通过 `towermd hub rebuild` 请求恢复，再在 App“项目态势”准备并确认恢复。恢复使用真实快照与原件，不重跑旧验证；CLI 没有人工确认命令。

### 托付：委托卡、验收与信任账本

本节对应[核心规格](specs/2026-10-21-spec-towermd-core.md) 4.7、6.1、6.3、6.5 节（FR-184、FR-185、FR-201–211）。

**委托卡。**创建任务就是填一张委托卡，5 栏顺序固定：目的、完成标准、边界、检查点、交付前自检。只有完成标准必填；没写时“委托”不可用。检查点每行一条，行尾写 `@ 2026-10-25 18:00` 即带上截止时间。Agent 用 `towermd task show` 读这张卡，同时读到这类工作已记下的规则和上次退回的理由。

**先澄清。**拿不准完成标准怎么写时，选“先澄清”。Agent 用 `towermd dev clarify` 交回复述、完成标准草稿和最多 3 个问题。你在澄清面板回答、改定完成标准，点“定稿并委托”后任务才能领取。定稿的卡片算人定内容。

**汇报请求。**带时间的检查点在领取时变成汇报请求，Agent 用 `towermd reply` 回应。到期没回应，Tower.md 记一次失联（见下文“提问、失联与兜圈子”）。没写时间的检查点只是 Agent 的停止点。汇报不算进度。

**验收卡。**Agent 收尾时用 `towermd dev finish --claims` 逐条写自述。验收卡按完成标准逐条列证据，证据分 3 类，形状、颜色和文字标签都不同：

- 检查：门禁或检查程序的结果，绑定提交。整体检查单列一行，不代替逐条证据。
- 受托者自述：Agent 自己说的，不能单独让任务完成。
- 我用过：你在验收卡上点“我用过”产生，只有人能产生。系统无法核实你是否真的用过。

一条证据也没有的条目标为“未证实”。你仍可以一步确认；确认时还未证实的条目会记下来，计入信任账本。开发任务由检查和合并完成，你的确认记为“已验收”。确认时可以写一句“这次改变了什么看法”，不强制，也不会提醒补写。

**退回与规则。**不满意就退回，写上理由。已合并的任务会重新变为可领取，理由进入下一次的任务卡。退回后 App 会问是否把这次纠正记为规则；确认后，规则进入以后同类工作的任务卡，不确认就只留在这次的记录里。

**信任账本。**账本按“受托者配置 × 工作类别”分行。配置是 Agent 领取时自报的 harness、版本、厂商、模型和技能包版本，任何一项变了都对新配置重新起算，旧记录保留，可以对照。工作类别默认取模块 ID，你可以改名或合并，系统不自动归类。每行汇总最近 20 次托付（`config.yaml` 的 `track_record_window`）：一次通过比例、按时比例、满足完成标准的比例、越界次数，以及实测的托付到交付时长、验收时长和退回次数。验收时长只计 App 内从打开验收卡到做出动作的时间。承诺弱化计这一配置在本次托付期间造成的弱化次数（见下文“承诺弱化”）；兜圈子计 Tower.md 对这一配置的托付判为兜圈子的次数（见下文“提问、失联与兜圈子”）。账本不打总分，不评价人，只存在本机和你的仓库里。

**委托级别。**级别同样按“配置 × 工作类别”设置，没设的继承项目级。默认 3 级：`report_only`、`answer_by_decision`、`approve_minor`，可在 `config.yaml` 的 `delegation_levels` 改。记录满一个窗口时，一次通过比例不低于 90% 会建议升一级，不高于 50% 会建议降一级。只给建议，级别只由你改。目前级别只记在账本上，还不改变 Agent 能做的事。

**抽查。**无论级别多高，已完成的任务都按比例抽出来请你复核，抽中的进入关注清单候选，确认或退回即消解。比例随一次通过比例下降，但不降到 0：默认最低 5%（`config.yaml` 的 `spot_check_min`，低于 1% 按 1% 算）。新配置没有记录，从 100% 起。

**待验收积压。**等你验收的事（待确认、待复核的抽查、待批准的提案）超过 5 件（`config.yaml` 的 `review_backlog`）时，首屏显示“N 件待验收”，委托按钮旁显示“先验收再托付”。这一行不占关注清单的 3 条名额，也不阻止委托。

**两种用法。**这两件事不做成功能，用现有的办法就能做到：

- 先写预期，再看结果。打开验收卡前，先写一句你对结果的判断，看完再对照。Tower.md 还没有旁注，可以先记在自己的笔记里；对照的结论写进“这次改变了什么看法”。
- 定期自己做一次。挑一类常托付的工作，隔一段时间自己做一次，免得验收的眼力退化。可以用跟进项给自己设个到点提醒（见下文“跟进项、休眠与浮现”）。Tower.md 不判断你该不该自己动手。

升级到本版本后，先运行 `towermd daemon stop` 停掉旧的守护进程。此前领取的运行不进入信任账本。

### 接入接口：汇报与提醒

本节对应[核心规格](specs/2026-10-21-spec-towermd-core.md) 第 5 节（FR-114–119）。任何受托者或来源——Agent、CI、定时脚本——都用同一个信封向 Tower.md 汇报进度、上报值得注意的事。入口有三个：命令行、本机 HTTP 和文件收件箱，三者走同一套校验，写入同一个事件流。

```sh
# 在任务工作树里：默认指向当前运行的任务，发送者是领取时自报的受托者
towermd report --state in_progress --summary "解析器完成一半" --next "补测试" --progress 3/7 --unit files

# 任意 shell 脚本：运行之外须用 --from 写明发送者，--target 省略时指向整个项目
towermd signal eng.crap --level active --title "CRAP 超过 30" --value 42 --threshold 30 --from ci/nightly --ref src/parser.rs
towermd signal ops.disk --level passive --title "磁盘已用 85%" --from cron/disk
```

- **汇报不算进度。**`--state` 只有 `not_started`、`in_progress`、`waiting`、`blocked`、`claimed_done`，没有 `done`；`claimed_done` 只是自称完成，任务是否完成仍由检查与合并决定。
- **级别由发送者声明，打扰方式由 Tower.md 决定。**`log` 只进时间线；`passive` 计入角标和摘要；`active` 进入关注清单；`time_sensitive` 排在关注清单前面。关注清单里它们显示为“告警”，并注明是谁自报的。
- **合并。**同一发送者对同一对象的同种上报合并为一条，保留最新的值并计数。发送者用较低级别（如 `passive`）再发一次同种上报，就能把它撤出关注清单；你也可以在 App 里处理它，见下一节。
- **长度。**标题不超过 30 字，摘要与说明不超过 100 字；超长直接拒绝（`too_long`），不截断。
- **种类带命名空间。**如 `eng.crap`、`ops.disk`；`core.` 开头的种类留给 Tower.md 自己。
- **署名。**事件由命令行记为 `process:towermd-cli`；`--from` 只是自报，不代表可信身份，也不能自称为人（`human:` 开头会被拒绝）。App 只读取这些上报，不代发。
- **重试。**沿用同一个 `--request-id` 重试得到同一条记录；内容不同则报冲突。

结果在守护进程 `/state` 的 `projection.TowerApi` 中：`reports` 每个发送者 × 对象一条，`signals` 每个发送者 × 种类 × 对象一条，各带 `count`、首末两次的事件号与署名。带时间的检查点生成的汇报请求，在 `delivered[]` 中同时附上同一信封格式的 `envelope`（`verb` 为 `request_report`）。

升级到本版本后，守护进程接口升到第 14 版，先运行 `towermd daemon stop` 停掉旧的守护进程。

#### 变化摘要

本节对应核心规格 FR-138、FR-139。扩展（或任何非人的来源）可以为一个任务或提案发一份**变化摘要**：最多 7 行，每行是“标签=值”，值是数字或一小段文字。Tower.md 只在固定位置原样显示，不解释内容；原文和 diff 留在对象本身，用 `--ref` 指过去。

```sh
towermd summary --line "新增函数=3" --line "新增依赖=1" --line "删除测试=1" --from pkg:eng-diff --target T-1 --ref abc1234
```

- **只拒绝，不截断。**多于 7 行、没有 `=`、标签超过 20 字、文字值超过 60 字、含控制字符，或带了 `label`、`value` 以外的字段，整条拒绝；值只能是数字或文字。
- **合并。**同一发送者对同一对象只保留最新一份，并计数；结果在 `/state` 的 `projection.TowerApi.summaries` 中。
- **显示在哪里。**`towermd since` 与项目内的 `towermd` 在 3 行摘要下逐份列出“变化 · 对象：标签：值；……（发送者 提供）”，一份一行，超过 120 字以“…”结尾；JSON 输出另有 `changes`，含完整的各行。App 的“自上次查看以来”同样逐份列出完整各行；关注清单上涉及该任务或提案的卡片多一个“为什么”，点开即是这些行。
- **权限。**与汇报、上报相同：三个入口都可发；`pkg:` 发送者须是 main 上已安装且清单无问题的扩展；摘要不算进度，也不会让任何东西完成。

#### HTTP 入口与文件入口

不方便调用命令行的来源可以直接发信封。信封就是 `delivered[]` 里 `envelope` 的格式，`project` 是 `.towermd/config.yaml` 中的 `project_id`：

```json
{"v":1,"project":"<project_id>","from":{"id":"ci/nightly","kind":"source"},"target":"<project_id>",
 "verb":"signal","data":{"kind":"ops.disk","level":"passive","title":"磁盘已用 85%"},"at":"2026-10-23T10:00:00+09:00"}
```

- **HTTP。**`POST http://127.0.0.1:<port>/tower`，请求体是一个信封。`port` 与 `instance` 来自 `towermd daemon ensure` 的输出；请求头须带 `x-towermd-instance: <instance>`，用来确认连的是当前这份守护进程，不是身份认证。只监听 127.0.0.1；认证与加密留待安全加固。项目须已在 App 中打开，否则返回 404。事件署名 `process:towermd-http`。内容完全相同的信封重发得到同一条记录。
- **文件。**把信封逐行写进 `<运行目录>/inbox/<project_id>/*.jsonl`（一行一个，单行不超过 64 KiB）。运行目录默认是 `~/Library/Application Support/towermd/runtime`，可用 `TOWERMD_RUNTIME_DIR` 改。文件 2 秒没有改动后，守护进程在下一次维护（约每 10 秒一次）取走它、逐行记成事件（署名 `process:towermd-file`），然后删除文件；被拒绝的行连同原因写到 `inbox/<project_id>/rejected/<文件名>`。收件箱在仓库之外，文件不会变成状态，也不会写进任何工作树。只处理 App 中打开着的项目；守护进程暂时出错时文件保留到下一次。
- **同一套规则。**两个入口与命令行一样拒绝 `human:` 发送者、超长文本、`core.` 种类和 `request_report` 等由 Tower.md 自己发出的动词，也受下面的扩展权限约束。命令行沿用 `process:towermd-cli` 署名。

#### 扩展：声明，不执行

本节对应核心规格 FR-120、FR-123。扩展是一份清单，声明某个来源会发哪些种类的上报、最高到哪一级；Tower.md 不加载、不运行扩展的代码，也不替它启动进程。扩展自己的脚本仍经上面三个入口发信封。

清单放在 `.towermd/extensions/<id>/towermd-plugin.yaml`，只从权威 main 读取：在 main 上即为已安装并启用，工作树里的改动不生效。`.towermd/` 整体是人定内容，所以安装、修改、卸载扩展都要经提案由你批准。

```yaml
id: eng-clean            # 必须与目录名相同；小写字母、数字、- 与 _
version: 1.2.0
type: check              # template、check、connector、skills、pack、kit；未知类型也接受
emits:
  - kind: eng.crap       # 只有本扩展能发这个种类
    label: CRAP
    icon: gauge
    unit: 分
    deterministic: true  # 声明后才可发确定性上报
    max_level: active    # 最高级别，省略为 active
commands:
  crap: cargo run -p probe -- functions   # 只是说明，Tower.md 不执行
```

- **查看。**`towermd ext ls` 列出 main 上的扩展、声明的种类和清单问题；`towermd ext show <id>` 显示一份清单的全部内容。命令行没有安装或启用命令。
- **发送者。**扩展以 `pkg:<id>[@版本][/部件]` 署名发送，如 `pkg:eng-clean@1.2/crap`。

| 情况 | 结果 |
| --- | --- |
| `pkg:` 发送者，扩展不在 main 上，或清单有问题 | 拒绝 |
| `pkg:` 发送者发清单没声明的种类 | 拒绝 |
| 级别高于该种类的 `max_level` | 拒绝 |
| 声明了 `--deterministic`，清单没写 `deterministic: true` | 拒绝 |
| 其他发送者发某个扩展声明的种类 | 拒绝（种类归该扩展所有） |
| 两个扩展声明同一种类 | 两份清单都记为有问题，二者都不能发送 |
| 其他发送者发没有扩展声明的种类 | 照常接受 |
| 以 `human:` 署名，或用 `core.` 种类 | 拒绝（与没有扩展时相同） |

**扩展的检查只能阻止，不能放行。**扩展的确定性上报和其他来源一样，可以让 `gates.yaml` 中同种类的硬检查判为“检查未通过”；但一项检查要算“通过”仍须守护进程验证器的结果。让验证器去运行扩展的命令就等于执行扩展代码，因此本版本不这样做。

### 容器与模板

本节对应核心规格 FR-141–158、FR-160–162、FR-187、FR-189。容器是画布上的一块区域，由模板决定怎么分栏，里面放卡片。容器本身只由你摆放；卡片由你在 App 中写，或由受托者按容器规则写。

- **放置。**打开项目后点右下角的“▭ 容器”，选一个模板，或者把模板拖到画布上。起个名字（不超过 60 字），可选写一句给受托者看的规则（不超过 300 字），选“由谁推进”，然后点“放到画布中央”或“放到拖放处”。新容器放在离那一点最近的空白处，画布上已有的卡片和容器都不移动。
- **移动与缩放。**拖容器的标题栏移动，拖边角缩放。松手后 App 向守护进程提交新位置；回执未知时容器停在你放的位置，栏里显示“尚未确认”，只能“重试原请求”或“放弃”。
- **只有人能动。**放置、移动、缩放都署名 `human:<id>`，只能从 App 发出；命令行发来的同类请求一律拒绝。请求里不能带署名或模板定义：守护进程按模板 ID 自己读取，并把定义冻结进容器，之后改模板不影响已放的容器。
- **模板。**内置 4 个：看板（kanban）、四象限（quadrant）、时间线（timeline）、思维导图（mindmap）。主干上的 `.towermd/extensions/<id>/towermd-plugin.yaml` 写 `type: template` 即为可用模板，同 ID 时替换内置模板；按状态分栏却没写 `states` 等问题会标出，不能放置。
- **角标。**`towermd signal <种类> --target <容器ID> ...` 指向某个容器时，该容器标题栏出现角标（▲ 需要注意 / ● 仅告知，并附文字）；`log` 级和已静音的不显示。

```sh
towermd template ls          # 模板、布局与问题
towermd frame show C-xxxxxxxx  # 容器的模板、规则与位置
```

命令行没有新建、移动或缩放容器的命令，也没有改规则或处理待办项的命令。容器记在 hub 事件里，随快照进入仓库；放置、改规则和接受待办项会立即发布一次快照，移动、缩放和卡片随下一次快照一起发布。

#### 卡片与规则

- **三种模式。**新建容器时可选：自由（默认，卡片都由人或受托者写）、绑定（卡片跟随核心对象，状态随对象变化，完成类状态只在对象按完成规则完成后才出现；不能另加卡片）、混合（绑定卡片之外还能加自由卡片）。绑定和混合可只列出部分对象，不列即全部。
- **你在 App 中写卡片。**容器标题栏点“+ 卡片”加卡片；点卡片可改状态或归档；“规则”里可以改规则文字、每栏上限、“更新到”日期、回看周期和是否关闭旁注。你的写入署名 `human:<id>`，不受容器规则限制。
- **受托者用命令行写卡片。**每次写入都按模板格式和容器规则检查，不合规的整条拒绝并说明原因，什么都不存：

```sh
towermd frame show C-reading                    # 写之前先读规则、状态和现有卡片
towermd frame add C-reading --title "读解析器" --state 待办 --field owner=bruce
towermd frame update C-reading.3 --body "补上错误处理" --clear due
towermd frame move C-reading.3 进行中
towermd frame link C-reading.3 C-reading.1       # 只有带关系线的模板可用
towermd frame archive C-reading.3
towermd frame propose C-reading rules.json       # 改规则只能提案
towermd frame edit C-plan change.json            # 只用于文本源容器，见下
```

  运行之外须用 `--from` 写明发送者。同一时刻一个容器只有一个写入者：第一次写入取得容器租约 60 秒，之后每次写入续期；别人持有时返回 `lease_busy`，稍后再试。

| 写入 | 结果 |
| --- | --- |
| 标题超长或多行、正文超长、状态不在模板里、字段不在规则里或类型不对、卡片不存在或已归档、违反流转规则、结构不支持上级或连线、规则要求来源却没有 ref 字段、规则只允许人做这件事 | 拒绝（`usage`），附原因 |
| 容器已过 `update_until`（日期已过，或指定对象已完成） | 拒绝，容器冻结为只读记录 |
| 合规，容器由人定 | 转为提案（虚线卡片），等你接受 |
| 合规，改的是你设定过的标题、正文、字段或状态 | 你设定过的部分转为建议，其余照常写入 |
| 合规，进入完成类状态且规则要求人确认 | 等你确认 |
| 改规则 | 一律转为规则提案 |
| 其余合规写入 | 直接写入；某栏超过每栏上限时仍写入，回执提示按规则合并或归档 |

- **待你处理。**提案、建议、确认和规则提案列在容器的“待处理”里，逐条“接受”或“忽略”；不会超时自动生效。接受时按容器的当前规则重新检查，已不适用的只能忽略。
- **每栏上限。**超过上限时，后到的卡片折叠为“+N”，已显示的卡片不移动。

#### 布局

本小节对应 FR-141、FR-144 方式 2、FR-149、FR-151。

- **卡片自己排布。**分栏、四象限按到达顺序排列；时间轴按日期排列，插入更早的日期只让后面的卡片顺延，顺序不变；思维导图按树生长，嵌套也画成树，每张新卡片单占一行；关系容器按到达顺序排成网格，卡片之间画关系线。归档卡片后，其后的卡片依次补位。
- **拖动即固定。**在 App 中把卡片拖到容器里的某处，它就固定在那里（标“◆ 已固定”），之后的布局只绕开它；点“◆ 已固定”取消固定，卡片回到推导位置。固定只能由你在 App 中做，署名 `human:<id>`，随下一次快照发布；命令行和受托者都不能固定。已冻结的容器不接受固定。`towermd frame show` 的 `pins` 列出固定位置（容器内坐标）。
- **跨容器连线。**连到其他容器卡片的线平时不画，悬停或点中一端时才显示；再点一次取消。
- **不打扰的刷新。**同一容器 1 秒内的多次更新合并为一次显示；容器的放置、移动、改名和固定立即显示，你自己的写入也立即显示。自上次查看以来变化过的卡片带一圈细边框。
- **变化高亮（FR-158）。**容器标题栏的范围选择可选“上次查看以来”“今天”“本周”“自某日”。选定后，这段时间里变化过的卡片带角标：“+ 新”“→ 状态”“✎ 文本”（形状、颜色和文字三者同时给出），其余卡片变淡；绑定卡片跟随核心对象，不在容器历史里，不变淡。选“不分类高亮”回到细边框。高亮只改颜色和角标，从不移动卡片。
- **时间滑块（FR-157）。**点标题栏“历史”，拖动滑块看容器在某一步时的样子：那时还没有的卡片隐去，改过的字段显示当时的值，这一步改了哪些卡片同样带角标。回放只读：看过去时不能加卡片、改规则、固定或处理待办项，标题栏显示“◷ 历史 · 只读”；点“回到现在”或“关闭”回到当前。每一步都从 hub 事件重放得到，不另存。
- **旁注（FR-160、FR-161）。**你回答的提问、发出的插话、记下的决策，或还没回答的提问，只要指向这个容器、它的某张卡片或它绑定的对象，就在那张卡片旁自动出现一条旁注，不超过 100 字：“◆ 为什么”（来自决策）、“✎ 调整”（来自回答或插话）、“? 问题”（还在等回答）。旁注跟着卡片走，不参与布局，也不挤动任何卡片；标题栏“旁注”可以按种类隐藏，“规则”里勾“关闭旁注”则这个容器不再生成旁注。旁注每次读取时推导，不存储。
- **回看周期（FR-156）。**“规则”里可以设“每隔几天回看”（1–365 天）。容器和项目、任务一样参与休眠与浮现（见下文“休眠”“浮现”）：距上一次写入满这么多天就以“↥ 浮现”提醒你回看，这个天数覆盖 `config.yaml` 中 `quiet.check_every` 对同一容器的设置；已冻结的容器是只读记录，不参与。目前只能改成另一个天数，不能清空。
- **按规则更新（FR-156）。**标题栏点“提问”，类别选“按规则更新”，写一句要求，选期限后发出。请求发给在这个容器上汇报过或写过卡片的受托者，以及声明能回答它的受托者；他们在 `delivered[]` 里收到，按容器规则改卡片，再用 `towermd reply` 回应。回应是自述，不算进度。“按规则更新”只能发给容器。
- **写入画布（FR-154）。**容器平时只在 hub 事件和快照里。要让它进入仓库的 `tower.canvas`，点标题栏“写入画布”：App 先显示要写的节点、所基于的主干提交和新文件全文，你读过后点“批准写入”。容器写成一个 `group` 节点（带 `towermd.container` 与 `towermd.template`）；由你定的容器，它的卡片也一并写入，位置取你固定的位置，没有固定的按网格排列；受托者推进的容器只写容器本身。写入由守护进程经唯一的主干写入者完成，并在 hub 记下批准和回执，`main_inspection` 据此证明这次提交；没有这份证明的 `tower.canvas` 改动仍被标为未证实。主干在预览后变了，或主干上还有未证实的提交时，批准会被拒绝，请重新点“写入画布”。回执未知时“重试批准”会找到已写入的提交，不会写第二次。
- **起步套装（FR-189）。**项目里有了第一个容器或第一次托付后，容器栏上方推荐起步套装：研究、写作（随 Tower.md 提供）和软件开发（随开发套件提供），列出建议先用的模板和名词的显示名称（例如写作把 Task 显示为“章节”）。每个套装只推荐一次，点“采用”或“忽略”都会记下，之后不再推荐；可以采用多个。套装不改变任何规则，也不自动放置模板。采用和忽略只能在 App 中做，署名 `human:<id>`。目前显示名称只在推荐里列出，还没有替换画布上的名词。
- **选中节点转为容器。**点画布左上角“选中节点转为容器”，点选节点（再点取消），点“转为容器”，然后在右下角的容器栏里选模板、起名字，点“转为容器”。字段映射是固定的：模板有状态和完成状态时，核心对象成为绑定卡片，状态跟随对象的阶段；其他节点复制成你写的自由卡片，标题截到模板上限；节点之间的连线在思维导图里成为上下级，在关系容器里成为关系线。新容器放在选中节点右侧最近的空白处，画布上的节点都不移动。思维导图和关系容器的初始布局由 elkjs 计算，结果作为你的固定位置写入；elkjs 只在这一步运行，快层更新从不调用它。每一步都是一次写入；中途某步失败时，已写入的部分保留，该步在容器栏里等你重试或放弃。

#### 文本源容器（PlantUML）

本小节对应 FR-163–169、FR-174–178、FR-180 与附录 A.2。

- **文件是唯一真相。**用“PlantUML”模板放容器时，指定仓库里的一个 `.puml` 或 `.plantuml` 文件（相对仓库根目录）；main 上还没有这个文件时勾“新建”，由写入者提交一个空图。容器每次读取都重新解析 main 上的文件，守护进程不另存元素；`towermd frame show` 的 `source` 给出解析结果。`.towermd/`、`.git/` 和受保护路径下的文件不能作为文本源。
- **支持的子集。**内置解析器 `builtin:plantuml-v1` 只认节点图：`@startuml`/`@enduml`（一个文件可有多张图）、`rectangle`、`component`、`node`、`package`、`folder`、`frame`、`cloud`、`database`、`actor`、`usecase`、`class`、`interface`、`participant` 等 33 种元素（`"名称" as 别名`、`<<构造型>>`、`#颜色`、`{ }` 嵌套或成员体）、`-->`、`..>` 等连线和 `: 标签`、`note … of …`（单行与多行，也可挂在连线上）、`!include` 仓库内文件（同一提交，最多 4 层）。C4 宏（`Person`、`System`、`Container`、`Rel` 等）显示为只读元素和连线。皮肤、标题、方向等语句不影响理解度；序列图片段、活动图等其余语句原样保留并计为未识别，画布显示“理解 N%”和未识别的行。不调用外部 Java 渲染器，也不显示原图。
- **状态与旁注映射。**模板的 `status_map` 把构造型或颜色映射为状态（默认 `<<todo>>` 待办、`<<wip>>` 进行中、`<<done>>` 完成），`callout_map` 把带构造型的 note 变成旁注（`<<why>>`、`<<adjust>>`、`<<question>>`）。没有别名的元素和未映射的构造型在检查里提示，不报错。
- **从画布或命令行改文件。**你在 App 中改状态、加元素、改名、连线或加旁注，受托者用 `towermd frame edit <容器> <change.json>`；每项修改由唯一的主干写入者打成最小的行补丁提交到 main，提交说明带 `Tower.md frame write: <容器>#<事件>`，hub 里记 `frame.source_written` 回执。受托者的修改按容器规则检查，由你定的容器转为提案；文件里找不到元素或文件无法解析时整条拒绝。直接编辑文件同样有效，合并到 main 后画布跟上。
- **写入失败留给你。**排队期间文件变了、修改不再适用时，这项写入以虚线留在容器里并写明原因，由你重做或放弃，不会自动重试改写。
- **文件坏了。**main 上的文件无法解析时，容器继续显示最后一个能解析的版本并锁定编辑，标出出错的行和修复建议；点开建议先看差异，再点 Fix 才写入（修复绑定文件的 sha256，只能由你在 App 中套用）。超过 24 小时仍未修好，或有绑定的未完成工作在等它时，提醒升为主动。
- **历史（FR-169）。**容器的“历史”列出改过这个文件的提交，每步按解析结果概括（“新增元素 1 个；Parser 状态由待办变为完成”）；点某一步只读查看那一版的文件。元素的位置由画布布局决定，你拖动过的元素按别名记住位置，不写进文件；只有名称、没有别名且含空格的元素不能固定。
- **文件改名或删除（FR-178）。**git 识别到改名时，容器提示新位置，由你在 App 中点“改为跟随它”；删除后容器显示“文件缺失”，不自动清理。

### 提问、失联与兜圈子

本节对应[核心规格](specs/2026-10-21-spec-towermd-core.md) FR-116、FR-126、FR-127、FR-137。

**在节点上提问。**在画布上选中任一节点，详情里的“提问”可以发出两类请求：“节点提问”问为什么、怎么做；“要求汇报”请人说明进度。写一句话，选期限（1 小时到 3 天），点“发出”。提问是你本人的动作，只能在 App 中做；命令行没有提问命令。收件人由守护进程决定，你不必也不能指定：

- 节点提问只发给声明过能回答这个节点的受托者。受托者或脚本汇报时加 `--answers` 声明（`towermd report --target <节点> --answers …`），用 `--no-answers` 撤回；声明一直有效，直到撤回。
- 没有人声明时，问题不丢：它排队等待，在关注清单以“无人可答”（图标 ∅）出现，谁之后声明了就发给谁。你也可以撤回它。
- 要求汇报还会发给在这个对象上汇报过的发送者，以及正在执行它的受托者。

收件人在之后任何一次 `towermd` 调用的 `delivered[]` 里收到请求，用 `towermd reply <request-id> --state <状态> --summary <回答>` 回答。回答节点提问须用 `--ref` 写明依据（文件、提交、文档），可重复；运行之外须用 `--from` 写明是谁在回答，且只有收件人能回答。节点详情列出每个请求的状态：已回答（谁、说了什么、依据）、等待谁、失联、无人可答、已撤回；还开着的可以撤回。回答是对方自述，不算进度，也不会自动记成决策。

**失联。**一个请求过了期限仍没人回答（检查点汇报请求同样适用），Tower.md 自己记一次失联：第一次只进“自上次查看以来”的摘要；同一对象上的前一个请求也失联过，就升为关注清单里的“失联”（图标 ◷）。失联由 Tower.md 署名（`process:towermd`），每个请求只记一次，之后回答了也不会自动消失，由你点“知道了”。撤回的请求和无人可答的请求不算失联。

**兜圈子。**Tower.md 只看事件，不懂业务，满足任一条就判为兜圈子，以“兜圈子”（图标 ↻）进入关注清单：

| 规则 | 默认 | `config.yaml` 的 `stuck:` 键 |
| --- | --- | --- |
| 同一对象的汇报连续多次写着基本相同的下一步 | 3 次 | `same_next` |
| 同一对象的同一项检查连续多次未通过（运行出错也算） | 3 次 | `check_failures` |
| 同一对象在一段时间内提问超过若干次 | 24 小时内超过 3 次 | `asks`、`ask_window_hours` |
| 一次托付进行的时长超过同类工作已完成托付中位数的若干倍（至少 3 个样本） | 3 倍 | `duration_factor` |

前三条只看最近 24 小时，开启时不会翻出旧账。阈值读得宽松：缺失、写错或不是正数的项沿用默认，不会因为笔误而关掉判断；把阈值调宽会被标为承诺弱化。每次判断只提醒一次；知道是哪次托付时，计入该受托者配置在信任账本上的“兜圈子”。提醒不暂停、不阻止任何事，是否插话、改写委托卡或暂停由你决定。

### 关注清单与“自上次查看以来”

本节对应[核心规格](specs/2026-10-21-spec-towermd-core.md) 第 7 节（FR-40–42、FR-128–131、FR-138）。

**每条一张卡，6 段固定。**关注清单的每一条都按同一顺序写成一行，不超过 100 字：何时 · 哪个对象：发生了什么。因为……。建议……。需要你：……。过长时先缩短最长的几段（以“…”结尾），时间、对象和“需要你”尽量保持完整。卡片前有形状和类别文字，不只靠颜色区分。

**排序。**先是时间敏感和涉及人定内容的（如“禁止”和 `time_sensitive` 提醒）；再是等你回答或批准的（提问、待批提案），等得最久的在前；其余按影响的对象多少排；到点的跟进项和浮现的对象排在最后。时间未知的排在同类最后。首屏只放 3 条，其余收在“另有 N 条已延后”里，画布上的项目卡也只显示这一行计数，不增加节点、不移动节点。

**名额。**首屏条数可以调小：在 `.towermd/config.yaml` 中写 `attention: { budget: 2 }`（1–3，默认 3；更大的值按 3 算，写错了按默认）。超出的照样收在“另有 N 条已延后”里，画布项目卡也按这个名额显示，不丢弃任何一条。

**打扰时机。**每条卡片上标出它什么时候找你，有形状也有文字：

| 时机 | 哪些 | 怎么找你 |
| --- | --- | --- |
| ‼ 立即 | `time_sensitive` 提醒 | 排在最前；App 开着时发一条系统通知 |
| ○ 下次查看 | 其余进关注清单的条目 | 只在清单里等你，不通知 |
| ≡ 摘要 | `passive` 提醒 | 只进“自上次查看以来” |

系统通知由 App 发出，守护进程从不发通知。每条提醒的每一次上报只通知一次；打开项目时已经在屏幕上的不再通知。时机是由级别推出来的，不另存。

**专注时段。**在 `config.yaml` 中写本地时间窗，如 `attention: { focus_time: ["09:00-12:00", "22:00-07:30"] }`，跨午夜的也可以；格式为 `HH:MM-HH:MM`，读不懂的窗口忽略。时段内清单上方注明只有必须停下的事会立即通知，其余等下次查看。目前只有 `time_sensitive` 会立即通知，所以专注时段还不改变通知本身；以后的授权请求会在专注时段内改为等下次查看。

**在卡上一步处理。**三类卡片可以不打开详情直接处理，只在 App 中提供，命令行没有对应命令：

- **提问**：点选项或在输入框写回答，记为“仅本次”。要记为模块决策，打开问题再答。涉及人定内容的回答仍转为待批准提案，不会直接生效。
- **待批提案**：已提交的提案有“批准”按钮。App 先准备出版预览，核对它与提案的草稿、项目和来源版本一致，再走与提案面板相同的批准；不一致就停下，请你打开提案重新审阅。会让承诺弱化的提案不提供一步批准，须打开完整审阅。
- **抽查**：“确认完成”与验收卡上的确认相同，记下验收时长和未证实的条目。

三者都署名 `human:local`，经守护进程写入。结果未确认时，清单下方给出“重试原回答”或“重试原批准”，沿用原请求号和全部原输入。没有任何一步会因为超时或无人处理而自动通过。

**知道了与静音。**`active`、`time_sensitive` 级的提醒卡下有两个按钮，只在 App 中提供，命令行没有对应命令：

- **知道了**：这条提醒离开关注清单，直到发送者再报一次。只对你看到的那一次生效；你打开后发送者又更新过，会要求你重新查看。
- **静音 7 天**：7 天内不再进入关注清单。发送者把级别升到高于静音时的级别（如从 `active` 升到 `time_sensitive`）会立刻重新出现。

两者都记为你本人（`human:local`）的事件，经守护进程写入，随事件日志可重放。已处理的条数显示在清单下方。

**自上次查看以来。**打开项目时，画布左上角显示一张 3 行摘要：完成了什么、卡在哪里、需要你做什么。离开不超过 24 小时且条数少时列名称，否则只给数目；“展开明细”可看逐条。`passive` 级提醒只在这里出现，同一对象收到 3 个以上来源的提醒时合成一条。

“上次查看”是你在本机最后一次关闭这个项目（切换项目或关闭窗口）的时间，只存在 App 的本地存储里，不写进仓库，也不进 hub。没有记录或记录读不出时，摘要改为“最近 7 天”。

### 跟进项、休眠与浮现

本节对应[核心规格](specs/2026-10-21-spec-towermd-core.md) FR-134–136。

**跟进项。**“任务与运行”面板下方的“跟进项”是你给自己设的到点提醒，最多 5 条未完成的。每条一句话（不超过 200 字）加一个到点条件：

| 条件 | 什么时候到点 |
| --- | --- |
| 到某个时间 | 到了你选的本地时间 |
| 某个对象完成时 | 这个任务的托付已完成 |
| 某个对象有新动静时 | 设下之后，这个对象上出现任何不是人发出的事件 |
| 某个对象出现信号时 | 设下之后，有人对这个对象发了信号；可以只等某一种信号 |

对象可以选项目本身或任意任务。到点的跟进项以“⚑ 跟进”进入关注清单，排在其他各类之后，只等下次查看，从不发通知。卡上有“完成跟进”；面板里的每一条也有“完成”。添加和完成只在 App 中提供，署名 `human:local`，命令行没有对应命令。跟进项是 hub 事件，守护进程重启后由快照和发件箱重建。

**休眠。**一个对象（项目或任务）超过 `dormant_after` 天没有任何事件，就进入休眠。租约、快照、hub 自身的记账事件不算。休眠的项目卡和任务依赖图上的任务卡变淡，并标“◌ 休眠”，位置不变；关于它的关注条目不占首屏名额，排到“另有 N 条已延后”的最后，并注明其中几条属于休眠对象。时间敏感和涉及人定内容的条目、到点的跟进项不受影响。项目本身休眠时，不指向具体对象的条目也随之延后。

**浮现。**休眠的对象在下面三种情况下重新浮现，卡片标“↥ 浮现”：

- 指向它的跟进项到点：随“⚑ 跟进”那一条出现，完成跟进即消解。
- 到了它的复查节奏：距上一个事件满 `check_every` 天（不论是否已休眠）。
- 连接器带来新动静：沉寂超过 `dormant_after` 天之后，来源（如 Note.md 连接器）对它发来汇报或信号。这是来源自报，不是证据。

后两种以“↥ 浮现”进入关注清单，卡上有“看过了”。你在这个对象上做任何动作（包括“看过了”）都会让它消解。浮现的条目附一张“上次到哪了”：上次的结论（最近一次确认完成的心得或汇报）、推翻过什么（退回理由、被驳回的提案）、未决的事（未回答的问题、未关闭的请求和跟进项），各最多 3 条。

休眠和浮现都由事件推出来，每次读取时现算，不另存。在 `.towermd/config.yaml` 中设置：

```yaml
quiet:
  dormant_after: 14      # 天，默认 14
  check_every:           # 按对象 ID 设复查节奏，单位天
    T-12: 7
```

天数取 1–3650，写错的值忽略，按默认处理。

### 检查：什么时候算完成

本节对应核心规格 FR-120–124。完成只认检查：对象的全部检查在当前版本上通过，才算完成；只有一项确定性检查都不适用的对象，才可由你在 App 中确认完成。开发任务总带一项内置检查 `core.verify`（`dev finish` 运行的模块验证命令），所以开发任务只能由检查和合并完成，你的确认记为“已验收”。

项目可以在 `.towermd/gates.yaml` 中另外声明检查。它是人定的内容：Agent 和命令行只能通过提案修改，守护进程只读权威 main 上的这一份，工作树里的改动不生效。

```yaml
gates:
  crap:                  # 检查名
    check: eng.crap      # 检查种类，与 towermd signal 的种类相同
    hard: true           # 省略即为 true；false 只提醒，不阻止
  style: eng.style       # 简写：只写种类，等同 hard: true
```

- **阻止。**任一来源对该对象发出的确定性上报（`towermd signal <种类> --deterministic`）达到 `active` 或 `time_sensitive` 时，同种类的硬检查判为“检查未通过”：`dev finish` 与 `dev trailers` 返回 `gate_failed`，App 也不接受确认完成。发送者以较低级别再发一次即解除。不带 `--deterministic` 的上报不影响检查。
- **放行。**上报只能阻止，不能放行：`--from` 是自报的。一项检查要算“通过”，须有守护进程验证器（`process:towermd-verifier`）在当前版本上的结果；目前只有内置的 `core.verify` 有这样的结果，其他种类在没有阻止上报时显示“未见阻止”。
- **出错即阻止。**`gates.yaml` 不是合法 YAML、某项缺 `check`、`hard` 不是布尔值、种类不合法，都判为“检查未通过”，直到人修好它。未知的键原样保留。
- **豁免。**对应核心规格 FR-03、FR-72。想在修好之前先放行，只能由你在 App 委托详情的“检查”一栏，对正在阻止该对象的那一项硬检查点“豁免…”，写一句理由、选有效天数（默认 7 天，最长 30 天）。豁免署名 `human:local`，只针对这一个对象的这一项检查；内置的 `core.verify`、软检查、声明有误的检查都不能豁免，命令行也不能授予（守护进程拒绝非 App 的请求）。豁免期间该项显示“已豁免”（↷），判断照常进行，`kind: gate` 证据里该项的证据列表第一条就是豁免 ID，豁免事件本身就是这次决定的记录。到期即失效，不写任何新记录，检查恢复阻止；豁免不续期，生效期间不能对同一项再授予，到期后需要时另行授予。到期前 24 小时，关注清单出现“豁免到期”（⌛）。
- **证据。**守护进程每次在 finish、trailers 或确认完成处作出判断，若项目声明了检查，就记一条 `kind: gate` 证据，写明对象、版本、读取的 main 提交与各项结果；`core.verify` 的结果是 `kind: check` 证据，绑定被验证的提交。
- **查看。**`towermd task show` 的 `delegation.card.completion` 与 App 委托详情的“检查”一栏列出每项检查的状态：检查通过、检查未通过、检查中、未见阻止、已豁免。

`gates.yaml`、`config.yaml` 和 `.towermd/extensions/` 是流程配置。主干上一个提交若只改了这些，关注清单把它标为“主干含未登记的流程配置变更（次要变更）”，告警详情带 `class: minor`；同时改了其他人定内容的仍是主要变更（`class: major`）。两者都照样阻止，直到你处理：流程配置不能认领或普通撤销，请用“转提案”登记。

### 中断与评审：任务停下等你

本节对应开发套件规格 10.2、12.1 节（FR-58）。开发任务的完成只认检查：每个运行都要过内置的 `core.verify`（受托者 `dev finish` 时守护进程真实执行的验证）；模块写着 `risk: high` 时，还要过计划评审（G1）和代码评审（G4）。“人确认完成”只用于非开发对象。

**什么会让任务中断。**下列情况任务进入“中断”（等待放行），关注清单出现对应的一项（中断 ⏸），点开后任务详情给出处理选项：

| 原因 | 关注清单 | 何时结束 |
| --- | --- | --- |
| 同一次运行验证连续 3 次未过（`core.verify` 或声明的硬检查） | “硬门禁自动修复次数用完” | 你选择处理方式，或豁免那项声明的检查 |
| `dev finish` 时路径守卫（G2）拦下越界或受保护的改动 | “改动被路径守卫拦截” | 你选择处理方式 |
| 领取时委托卡缺允许路径、验收标准或主干上的相关决策（G0） | “委托卡缺信息，任务未派出” | 你定稿委托卡补上信息，或选择处理方式 |
| 运行出错、预算用完（见下节） | “错误”“预算” | 你选择处理方式 |
| 受托者提问或请求评审 | 问题、评审 | 回答或给出评审结论，任务自动恢复 |

验证未过的次数和运行失败的次数分开计：前者按同一运行的验证结果计，第 3 次才中断，前两次受托者照常修；后者是运行器看到的失败。领取时缺信息会同时问到任务的创建者，受托者收到 `gate_failed` 并停下；同一中断未处理前不重复提问。中断不改变节点位置，只改颜色和角标。

**处理选项。**在 App 的任务详情里选择，署名 `human:local`，命令行不能处理：

- **让 Agent 再修**：中断结束，失败计数清零，同一运行继续；没有运行的任务回到就绪。
- **改写任务**：结束当前运行、释放模块租约，任务回到待定稿，由你改写委托卡后再派。
- **重派**：结束当前运行、释放模块租约，任务回到就绪，可由别的受托者领取。
- **豁免…**：只对声明在 `gates.yaml` 里的硬检查出现，规则同上节（默认 7 天，最长 30 天，不续期）；`core.verify`、评审和路径守卫都不能豁免。

没有“直接通过”的选项：中断不会超时放行，处理也不会把任务标为完成，进度仍只认证据。

**重派正在执行的任务。**没有中断时，任务详情的运行列表里，当前运行旁也有“重派”：结束这个运行、释放模块租约，任务回到就绪。按钮带着你看到的运行 ID；运行已经换了时守护进程拒绝（`conflict`），刷新后再操作。“请求暂停”和“要求汇报”仍是插话，受托者在下一个检查点读到，任务状态不变。这三项都署名 `human:local`，只能在 App 中做。

**请人评审。**受托者在运行中用 `towermd ask "<摘要>" --review plan|code [--artifact <路径>]` 请评审，返回评审 ID（`V-…`）并以退出码 5 表示等待；`towermd wait <V-…>` 再等最长 90 秒。评审期间任务中断，关注清单出现“评审”（⚖），你在 App 的任务详情里选“通过”“要求修改”或“驳回”，后两者须写意见。

- **G1 计划评审**绑定当前这次运行：`dev finish` 开始前，若这次运行请过计划评审或模块是高风险，最近一次结论须为“通过”。
- **G4 代码评审**绑定最近一次通过 `dev finish` 的代码版本（tree）：`dev trailers` 前同样须为“通过”。所以先 finish 再请代码评审；之后改了代码要重新 finish、重新请评审。
- 评审不会因等待超时而通过，未处理的评审会一直阻止 finish 或 trailers。

### 无头运行：适配器、运行报告与预算（M3 预览）

本节对应开发套件规格 10.3–10.5、12.1、14.3 节（FR-25–29）。无头运行的部件已经就位，但还没有调度器去启动它们（M3-B），所以目前你能直接用到的只有 `dev finish --report` 和 App 里的两类新中断。

**适配器。**Claude Code、Codex、Cursor（`agent`）和 Gemini 各有一个适配器，只有它们知道各自的命令行参数和输出格式。运行器把一切需要的配置写在命令行上，不读写你的全局 harness 配置：

| harness | 启动方式 | 费用 |
| --- | --- | --- |
| Claude Code | `claude --bare -p --output-format stream-json`，带报告的 JSON Schema、权限模式、预算上限和显式的技能目录 | 报告 |
| Codex | `codex exec --json`，沙箱、报告 Schema 文件，提示从标准输入读 | 不报告，记为未知 |
| Cursor | `agent -p --output-format stream-json` | 不报告，记为未知 |
| Gemini | `gemini --output-format stream-json`（只有模拟测试） | 不报告，记为未知 |

运行器把任务卡和报告 Schema 写到 `<git 公共目录>/towermd/runs/<运行>/`，harness 的原始输出原样留在同一目录的 `output.jsonl`。这些文件只在本机，不是状态，删掉不影响重放。停止运行时先发 SIGINT，等最多 60 秒，再发 SIGTERM，最后 SIGKILL。

**运行报告。**Agent 结束前写一份运行报告：状态（`done`、`blocked`、`needs_input`、`needs_decision`、`failed`）、不超过 300 字的摘要、检查点提交、改动路径、问题、怀疑的错误类别和提案。手动收尾时可以带上：

```bash
towermd dev finish --claims claims.json --report report.json
```

报告和 `--claims` 一样只是自述：记在证据请求里，不让任务完成，也不改变任务状态。格式不对（摘要为空或过长、检查点不是提交号、路径越出工作树）会被拒收。

**错误中断。**运行器自己观察到的结果才会移动任务：运行失败（没写报告、退出码非零、超时）任务变为“运行失败”，释放运行后回到就绪；harness 崩溃，或同一任务失败满 3 次，任务进入等待放行，关注清单出现“错误”。报告里怀疑是设计类错误时也出现“错误”，但任务状态不变。外部错误（限流、断网、认证）在同一次运行内自动重试。错误分 3 类：外部、执行、设计。同一类错误 24 小时内出现 3 次是一个信号。阈值和预算写在 `config.yaml` 中，调度器接入后生效：

```yaml
signals:
  repeated_error: { count: 3, window_hours: 24 }
budget:
  run_usd: 2          # 每次运行的上限（美元）
  module_usd: 20      # 每个模块累计的上限
```

**预算中断。**运行或模块达到预算上限时，运行停止并保留检查点，任务进入等待放行，关注清单出现“预算”。harness 没报告费用时记为未知，不记为 0：设了预算却费用未知，就出现“预算”中断请你决定，不让运行悄悄通过；不报告费用的 harness 在设了预算时不会启动。

**交互网关。**（规格 16.4 节，FR-60、FR-63）能接 MCP 工具的 harness（目前是 Claude Code）在无头运行中会拿到交互网关：运行器把配置写进 `<git 公共目录>/towermd/runs/<运行>/mcp.json` 并在命令行上显式传入，不改你的 harness 配置。网关是隐藏命令 `towermd mcp --run <运行> --worktree <工作树> --harness <适配器>`，由 harness 启动，你不用手动运行。它只是本机守护进程的客户端：守护进程没在运行时它不会去启动，只服务运行器启动且仍在运行的运行，事件以该运行的 Agent 署名。它提供 4 个工具，没有一个能批准任何事：

| 工具 | 作用 |
| --- | --- |
| `towermd_ask` | 向你提问，最多等 10 分钟；没人回答时问题转为停车，Agent 以 `needs_input` 结束本回合 |
| `towermd_request_review` | 请求计划（plan）或代码（code）评审；评审从不因等待而通过，仍未结论时同样以 `needs_input` 结束 |
| `towermd_permission` | 由 harness 在工具需要授权时调用（见下） |
| `towermd_note` | 留一条进度说明，不等待；它只是自述，不算进度 |

**授权。**Agent 要用未放行的工具时，关注清单出现“授权”（⚿）一项，写明工具和输入。在 App 里选“本次允许”或“拒绝”，只对这一次有效。10 分钟内没人回答即拒绝，运行结束时仍未回答的也一并拒绝，都由 `process:towermd` 记录；网关连不上守护进程、请求读不懂时同样按拒绝处理。只有交互网关能申请授权，只有 App 能回答，命令行没有对应命令。“写入允许规则（L3 登记）”这一选项尚未提供。

**技能包锁定。**（开发套件规格 10.6 节，FR-51–54）无头运行只加载仓库里锁定的工作流技能包。由你把技能包复制到 `.towermd/skillpacks/<名称>@<版本>/`（技能放在 `skills/<技能>/SKILL.md`），在 `.towermd/skillpacks.yaml` 登记并提交；两者都是 L3 流程配置，改动按流程变更登记：

```yaml
packs:
  - type: SkillPack
    name: superpowers
    version: 1.2.0
    origin: https://github.com/obra/superpowers
    hash: sha256:<64 位十六进制>
    enabled_for:
      controller: [brainstorming, writing-plans]
      executor: [writing-plans, test-driven-development, verification-before-completion]
      reviewer: []
    disabled: [using-git-worktrees, finishing-a-development-branch]
    interaction_points:
      brainstorming: { maps_to: hold.question, scope: slow_layer }
      requesting-code-review: { maps_to: gate.G4 }
```

`hash` 在技能包目录里这样算：

```bash
cd .towermd/skillpacks/superpowers@1.2.0
find . -type f -print0 | LC_ALL=C sort -z | xargs -0 shasum -a 256 | shasum -a 256
```

每次运行从已提交的版本读取锁定内容（工作树里未提交的改动不算），核对哈希后，只把所属角色启用的技能复制到 `<git 公共目录>/towermd/runs/<运行>/skillpacks/<名称>/skills/`，再按适配器的方式显式交给 harness；禁用的技能和其他角色的技能都不复制。角色只有 `controller`、`executor`、`reviewer`；交互点只能映射到 `hold.question`、`hold.review` 或 `gate.G0`–`gate.G6`。哈希不符、副本没提交、启用了包里没有的技能、同一技能既启用又禁用，或锁定文件有误时，运行不启动。没有 `skillpacks.yaml` 时不加载任何技能包。你自己 harness 里装的技能不受影响（FR-108）。

调度器（M3-B）接入前，交互网关与技能包组装还不会被自动启动。

### 承诺弱化

本节对应核心规格 FR-125。完成标准、检查或门禁被放宽时，Tower.md 自己判断并提醒你。提醒以“承诺弱化”出现在关注清单靠前的位置（图标 ⇣），由 Tower.md 署名（`process:towermd`），不是来源自报。提醒不批准、不阻止任何事：改动本身仍要你在 App 里批准才生效。

| 算弱化 | 不算（判断不了就不报） |
| --- | --- |
| `gates.yaml` 删掉一项检查，且没有别的门禁仍检查同一种类 | 新增、改名、由软改硬 |
| 硬门禁改为软（`hard: false`），且没有别的硬门禁仍检查同一种类 | 任一边的 `gates.yaml` 读不懂 |
| 门禁写上 `deterministic: false` | 改写措辞、调换顺序 |
| `config.yaml` 的 `review_backlog` 调高、`spot_check_min` 调低（按生效值比） | 其他阈值，以及扩展自定义的阈值 |
| 完成标准（委托卡的 `done_when`、验收标准）条数变少 | 条数不变而内容改写（是否放宽无法判定） |
| 模块或验收的验证命令被删掉，且同一提案里别处不再有同一条命令 | 命令挪到另一个模块 |

在这些地方检查：

- **提案。**提交或捕获提案时检查它带的改动，提醒指向这份提案。App 的提案详情另列“这是弱化”一栏，逐条写明放宽了什么；批准即接受这些放宽，不同意就驳回。
- **澄清。**受托者用 `towermd dev clarify` 起草的完成标准比委托卡上原有的少时，提醒指向这张委托卡。你在 App 里定稿时若删减了完成标准，面板标出“这是弱化”；定稿本身就是你的决定，不再另发提醒。
- **主干。**守护进程核对主干时，比较上次核对过的版本与当前版本的 `gates.yaml` 和 `config.yaml`，提醒指向项目。

同一来源只提醒一次，重试或多台主机都不会重复。由运行中提交的提案或受托者的澄清造成的弱化，计入该受托者配置在信任账本上的“削弱标准”；主干上的改动不归到任何配置。

### 生长信号与定型

本节对应[开发套件规格](specs/2026-10-21-spec-towermd-development-kit.md) 9.2、9.3。有了经你批准的版本后，守护进程每次核对主干都按已批准模块的允许路径给主干上的源码文件归属，再结合最近的任务和运行记录测量下面五个信号。越过阈值时由 Tower.md 署名（`process:towermd`）进入关注清单，详情写“Tower.md 测得”，建议让会话中的 Agent 起草提案（`towermd propose`），由你在 App 批准或驳回。信号本身不改变任何结构；回到阈值以内时自动消失，再次越过会重新提醒，不重复刷屏。

| 信号 | 计算方式 | 默认阈值 | `config.yaml` 的 `signals:` 键 |
| --- | --- | --- | --- |
| 模块过大 | 模块内源码行数或文件数 | 超过 3000 行或 40 个文件 | `module_size: { lines, files }` |
| 跨模块改动 | 最近 10 个任务中声明了 `touches` 的比例（不足 10 个任务时不判断） | 超过 30% | `cross_module: { window, ratio }` |
| 未划分区膨胀 | 不属于任何已批准模块的源码文件数 | 超过 10 个 | `unassigned: { files }` |
| 需求未分配 | 主干上意图的 `allocated_to` 为空 | 存在即提醒 | — |
| 同类错误反复 | 同一错误类别在窗口内出现次数 | 24 小时内 3 次 | `repeated_error: { count, window_hours }` |

阈值读得宽松：缺失、写错或不是正数的项沿用默认。行数只计 Tower.md 能读出的文本源码（单个文件不超过 1 MiB）。

**生长期与定型期。**项目默认处于生长期，允许未划分区存在，超过阈值才提醒。在 `config.yaml` 写 `growth: { mode: settled }` 手动切到定型期，或写 `growth: { settle_at_modules: 6 }` 让已批准模块数达到 6 个时自动定型；没写就一直是生长期，不设默认数。定型期内任何一个未划分文件都会提醒。定型期对提案影响分析、接口契约和默认验证的更严要求尚未落地。

### 读取哪份内容

- 没有 `origin`：读取本地 `refs/heads/main`。
- 存在 `origin`：读取已 fetch 的 `refs/remotes/origin/main`。请自行完成 `git fetch origin`；App 不自动访问远端。
- 配置、对象、画布坐标与文件原文均来自同一固定提交。其他分支和未提交修改不会进入画布。
- `tower.canvas` 位于 `.towermd/config.yaml` 中的 `docs_dir` 下；文件节点路径以仓库根为基准。

没有配置时，App 显示初始化说明；已有配置但没有画布时，可主动扫描并验证生成候选。引用缺失或画布条目非法时，可在“项目态势”查看诊断。

### 连接 Note.md

Tower.md 与 Note.md 只互相引用：Tower.md 不存长篇知识，Note.md 不存执行状态。默认不连接，不报错。要连接，在 `.towermd/config.yaml` 中写明知识库目录，并提交到权威 main：

```yaml
notemd:
  vault: ~/notes   # 绝对路径、~/ 开头，或相对仓库根
```

**回写（Tower.md → Note.md）。**守护进程每轮维护（约 10 秒）检查一次，把两类结果各写成一份纯 `.md` 摘要，放进知识库的捕获目录 `{vault}/{inboxDir}/towermd/`（`inboxDir` 取 Note.md 的 `.notemd/settings.json`，没设时为 `inbox`）：

- 已合并的任务：`task-<任务ID>-<提交前7位>.md`，写为什么做、合入提交与完成标准。重开后再次合并会另写一份。
- 已接受的决策（`status: accepted` 或 `stable`）：`decision-<决策ID>.md`，写问题、结论与它引用的 Note.md 知识。

摘要是 OKF v0.2 文档，`generated.by` 为 `process:towermd`，`sources` 指回合入提交和 Tower.md 对象：

```markdown
---
type: Decision Summary
title: 决策 D-7：用哪种共识？
description: 用 Raft
tags: [towermd]
generated: { by: process:towermd, at: 2026-10-23T08:00:00Z }
sources:
  - { id: commit, resource: git:<提交>, title: 提交 1a2b3c4 }
  - { id: decision, resource: towermd:<project_id>/D-7, title: Tower.md 决策 D-7 }
  - { id: note-1, resource: kb/raft.md, okf_id: kb/raft, block: b-00ff00 }
---
# 决策 D-7：用哪种共识？

问题：用哪种共识？

用 Raft

在 Tower.md 中接受（决策 D-7[^decision]），记录于提交 `1a2b3c4`。[^commit]

引用的 Note.md 知识：

- `((kb/raft.md#b-00ff00))`[^note-1]
```

回写只做这些事：只写 `.md`，从不写 `.note.md`，不加链接、不结网；文件名固定，只新建、从不覆盖，你改过、挪走或删掉的摘要不会被重写；不碰知识库里已有的文件，也不在知识库里运行 git。整理、链接与收进知识网仍由你在 Note.md 里做。第一次连接（或换了知识库）时只记下现有的任务和决策，不倒灌旧账，之后新出现的才写。记录存在本机运行目录，删掉只会让下一轮重新记一遍，不会重写。知识库位于本项目仓库内时拒绝回写。写入失败只在守护进程日志里提示，下一轮重试。

**引用（Note.md → Tower.md）。**提案输入可以带 `sources`，记下依据的 Note.md 知识：`okf_id` 是概念路径去掉 `.md`，`block` 是块 ID（Note.md 块引用 `((kb/raft.md#b-00ff00))` 中 `#` 之后的部分），可选 `path` 与 `title`。格式见[提案技能](../skills/towermd-propose/SKILL.md)。批准后它们写进出版的决策的 `sources`，决策摘要再把块引用列出来。读取时宽容：不认识或写错的来源条目原样保留，不会让对象被拒绝。

### 多台机器共用一个 hub（可选，自部署）

默认每台机器用本机 hub，不需要任何账号或云服务。几台机器要协作同一个项目时，可以自己部署一个云端 hub，让它成为这个项目唯一的定序者。

> **当前仅适合可信网络/自用。**云端 hub 还没有认证和加密：知道地址的人都能读写这个项目的事件流。只部署在你自己的账号下，地址不要公开；`.towermd/config.yaml` 里不要写任何密钥。

**部署（由你自己完成）。**仓库的 `hub-worker/` 是一个 Cloudflare Worker，每个项目对应一个 SQLite Durable Object：

```sh
cd hub-worker
pnpm install --ignore-workspace
pnpm test             # 本地 workerd 里跑协议测试，不需要账号
pnpm exec wrangler login
pnpm run deploy       # 部署到你自己的 Cloudflare 账号
```

本机试用可以 `pnpm dev --port 8799`，地址是 `ws://127.0.0.1:8799`。

**配置。**在 `.towermd/config.yaml` 写明 hub 地址，并提交到权威 main，让每台机器读到同一个地址：

```yaml
hub:
  url: ws://hub.example.internal:8799   # 只支持 ws://
```

- 不写 `hub` 就是本机 hub。`hub` 写成空值或写错时，项目拒绝打开并给出原因，不会悄悄退回本机。
- 地址里不能带用户名、密码、查询参数或片段，以免把密钥写进仓库。
- 本版本没有内置 TLS，`wss://` 会被拒绝；部署在 Cloudflare 上时只能经可信网络内的 `ws://` 入口访问（例如自建反向代理或隧道）。
- 各台机器还要共用同一个 git origin：持有主干租约的守护进程把快照推到 origin 的 main，其他机器从那里读取。

**离线时会怎样。**

- 打开项目需要连上 hub；连不上时项目态势显示“hub 离线，暂时无法读取”，不会在本机另起一个定序者。
- 普通事件（汇报、提醒、Agent 记录等）离线时进入本机发件箱，命令返回 hub 离线（HTTP 503，CLI 退出码 8）并写明事件 ID；重连后按原事件 ID 重发，hub 按事件 ID 去重，重发多少次都只记一次。
- 人的操作不排队：离线时直接失败，重连后再做。
- 领取任务、续租、释放和主干租约都必须在线；离线时明确失败，不会退回本机定序。
- 只有持有主干租约的那台机器写快照和慢层；其他机器只跟随。主干租约过期后，另一台机器在线时才能接手。
- 租约到期以 hub 的时钟为准；各台机器的时钟应大致同步。

**暂不支持。**从本机 hub 迁移到云端 hub、云端 hub 的重建与恢复（`towermd hub rebuild`）、离线冷启动。要换 hub，请在没有进行中的任务时改配置。

## CLI 入口

CLI 提供初始化、扫描与综合草稿、任务领取与证据、问答、提案、快照与守护进程管理。随包程序位于 `Tower.md.app/Contents/MacOS/towermd`，可使用完整路径调用，或在当前终端将该目录加入 PATH。查看准确参数：

```sh
cargo run -p towermd -- --help
cargo run -p towermd -- init --help
```

只有在准备初始化一个项目时，才运行下面的命令，并将占位路径替换为实际仓库：

```sh
cargo run -p towermd -- init /path/to/project --docs-dir docs/tower
```

`init` 只生成项目 ID、配置、Agent 说明与文档目录骨架，不生成模块图、运行任务或提交 Git。已有 Tower.md 项目应沿用原配置和文档，不要用示例覆盖已有文件。检查生成内容后，自行决定如何提交；首次导入已有内容的提交不等于 B0 批准。

仅执行 `init` 不会产生模块图。将配置提交到权威 main 后，可在 App 扫描，或在项目目录运行随包 `towermd`：

```sh
towermd show
towermd dev scan start
towermd dev scan wait <返回的扫描ID>
towermd dev scan show <扫描ID>
towermd dev scan cancel <扫描ID>
```

扫描会实际执行候选命令，立即返回 ID；等待每次最多 85 秒，仍在运行时可继续等同一个 ID。`ready` 表示报告已经生成，不代表所有测试通过，须查看模块与命令的实际状态。取消也需要等原 ID 进入终态，不能把请求已接受当作进程已结束。CLI 没有批准命令。同一 clone 的多个工作树共用项目服务；同一 project_id 的独立 clone 不可同时打开。

任务范围外想到的事，用一句话记成想法，而不是新建任务：

```sh
towermd idea add "给周报加 CSV 导出"
```

想法一行写完，不超过 200 字，署名 `process:towermd-cli`；同一 `--request-id` 重试得到同一条想法。命令行没有立项命令，想法只能由人在 App 中立项。

还没有批准版本时，用一句话（或已立项的目标）取得第一个版本的种子计划：

```sh
towermd dev seed "做一个把会议录音转成待办的命令行工具"
towermd dev seed
```

它返回草稿意图 I-1、骨架上限与步骤，不写入任何内容；批准仍只在 App 中进行。

### 在终端里看

本节对应[命令行规格](specs/2026-10-21-spec-towermd-cli.md) 2.1、2.4、2.6 节（C1）。下面的命令都只读，从不批准，也不替人做任何动作：

```sh
towermd                      # 项目里：3 行“自上次查看以来”和最多 3 条关注项；项目外：全部项目总览
towermd needs [--all]        # 关注清单，顺序与 App 相同；--all 列出全部
towermd since [--from 2h]    # 自上次查看（或指定时间）以来的 3 行摘要，及其间收到的变化摘要
towermd overview             # 本机全部项目的健康色、待处理件数、最近活动和跨项目关注清单；从不启动守护进程
towermd show T-2             # 任何对象；不带 ID 或用项目 ID 时是项目画布
towermd ls tasks --state ready [--since 1d]   # 种类：tasks、decisions、proposals、frames、follow-ups、ideas、holds
towermd history T-2          # 对象的时间线，只有事件元数据，不含正文
towermd watch [--scope T-2]  # 持续输出事件；JSON 模式下每行一个信封
towermd open [ID]            # 在 App 中打开项目；暂时还不能定位到对象
towermd decision ls / decision show <ID> / rule ls   # rule ls 含生效中的临时规则
towermd doctor / whoami / rebuild-index
towermd completion zsh > ~/.zfunc/_towermd
```

- **关注项只给“看”的命令。**每条关注项后面附 `towermd show <ID>` 或 `towermd open`。回答、批准、确认都在 App 中完成。
- **上次查看。**人在终端里运行 `towermd`、`needs` 或 `since` 时，才更新“上次查看”的时间；Agent 调用（输出不是终端）不更新。它记在运行目录的 `views.json` 中，与 App 的“上次查看”分开保存，删掉只会丢失已知项目列表和查看时间。
- **多项目总览。**`towermd overview` 与 App 菜单中的“全部项目”读同一份数据（守护进程的 `GET /overview`）：本机在 App 中打开过或运行过 `towermd` 的项目，各带健康色、待处理件数、最近活动时间，以及完成、进行中、受阻件数、最近检查结果和按模块的同样汇总；下面是一份跨项目关注清单，排序与单个项目相同，首屏最多 3 条。健康色总带形状和文字：▲ 需处理（禁止、检查未通过、受阻，或阻塞受托者的待批提案）、◆ 需留意（待回答、待评审、受阻对象，运行中的任务超过 `health.no_progress_hours` 小时没有已确认的进展，或同一对象被 3 个以上来源提醒）、● 正常、○ 没有任务。阈值在 `.towermd/config.yaml` 中设，默认 24：`health: { no_progress_hours: 24 }`。守护进程没有运行时，`overview` 只列出项目，状态为 `unknown`。总览全部由事件派生，每次读取时重算。
- **`--project`。**可以写项目路径或项目 ID；ID 须是当前仓库的，或本用户运行过 `towermd` 的项目。找不到时报 `not_found`，并提示运行 `towermd overview`。
- **任务。**`towermd task ls [--state ready]` 等同于 `ls tasks`。`towermd task edit <文件>` 重写一个由命令行建、尚未领取的任务；人建的任务、人已定稿委托卡的任务都不能改。`towermd task claim` 不带 ID 时，只有恰好一个任务可领取才领取它；有多个时报 `usage` 并列出候选，一个都没有时报 `not_found`。`task claim` 与 `task show` 先打印完整任务卡：模块、涉及模块、允许路径、基线、验收、验证命令、接口、决策、禁止事项、交互方式、生效的规则、最近 5 条插话、检查点和汇报方式；`--json` 输出在 `task_card` 中给出同样的字段和 `markdown`。
- **等待。**`towermd wait <ID> [--seconds N]` 既能等回答（`H-…`），也能等完成验证（`E-…`）。单次最多 85 秒，没等到时退出码为 5，按 `next` 再等。
- **`doctor`** 只检查本机：git、守护进程是否在运行以及版本是否一致、当前项目的 hub 配置，不上传任何内容，也不启动守护进程。**`whoami`** 说明这次调用会被记成 `process:towermd-cli`，不能代替人。**`rebuild-index`** 目前没有本机索引可重建，状态由守护进程从快照重建。

升级到本版本后，守护进程接口升到第 14 版，先运行 `towermd daemon stop` 停掉旧的守护进程。
