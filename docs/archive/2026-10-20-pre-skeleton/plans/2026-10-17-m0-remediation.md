### D1 没有远端、且 `main` 已检出时，快照写到哪里（FR-91）

**现状**：工作区规格改成了"一律推迟"（标注 10-17 人确认），代码也照此实现（`snapshot_git.rs:71-78`）。单人、无远端的仓库，通常就在主工作树上检出 `main`，这样快照永远写不出来。推迟时不提示，每秒重试一次，NFR-02 里"丢失范围不超过一个快照间隔"的上界就失效了。

已提交的原文用 `commit --only` 在用户的工作树里提交，这本身和"不得触碰工作树"相矛盾，所以退回原文也不对。

- ★ A：`main` 已检出时，快照提交写到私有引用 `refs/towermd/snapshot`，用带旧值校验的 `update-ref`。这个引用不是分支，不移动任何分支，也不碰工作树和 index。恢复时在 `main` 与该引用中取 `(epoch, seq)` 最大的快照。等 `main` 不再检出，或配置了远端后，再把最新快照按常规路径写回 `main`。删掉 hub 目录后，该引用仍在，能起到快照的作用。
- B：保留"推迟"，但加上提醒和上限：`status` 显示推迟原因和推迟了多久；超过 `snapshot_interval` 时发 `alert.raised`；重试改为退避。这样丢失窗口仍然没有上界，只是用户知道了。
- C：退回原文的 `commit --only`。不推荐，它会改动用户的 index。

### D2 M0 里 hub 能否真正重建（FR-93，16.1）

**现状**：工作区规格新增了"M0 的 CLI 只能请求恢复"。代码里 `AppConfirmation` 的字段全是私有的，产品路径构造不出它。M0 验收"删掉本地 hub 后能从快照重建"只在单元测试里成立。

- ★ A：守护进程实现给 App 用的确认端点 `POST /hub/rebuild/:request_id/confirm`，只接受客户端类型为 App 的请求（v0.1 按客户端类型区分，见 16.2 节），由它构造确认并执行重建。M0 验收改为"以 App 客户端身份调用该端点，端到端重建成功"；真人点击放到 M1 验收。CLI 仍然只能发起请求，不违反"CLI 不提供批准类命令"。
- B：M0 允许在终端里交互确认后执行。这违反 FR-95 和 FR-111，不推荐。
- C：把这条验收挪到 M1，M0 不做。

### D3 S5 用什么机制运行测试（第 8 节 S5，FR-107）

**现状**：S5 验证器把 blob 物化到一个不含 `.git` 的临时目录，外面套 `sandbox-exec`，禁网并清空环境变量。FR-107 规定的是在 git 公共目录下用 `git worktree add --detach` 建临时工作树。这样同一条验证命令在 S5 和 `finish` 里会走两套机制，证据的语义也不一致。沙箱在规格里属于没排期的"安全加固"。

- ★ A：统一到 FR-107 的分离工作树，S5 和 `finish` 共用同一个验证器。继承用户的环境变量，让工具链和依赖缓存可用；不禁网；设超时，到时回收整个进程组。规格里 S5 的"只读工作树"改写为"不触碰用户工作树的临时分离工作树"。沙箱实现留在 `/private/tmp` 的工作树里，归入安全加固的待办。
- B：保留沙箱，修改 FR-107，让 `finish` 也走沙箱。这需要解决环境变量和网络导致的误报失败，代价大，而且属于 M1 的范围。

### D4 `init` 的推送检查（FR-91 末句）

**现状**：规格写"`init` 检查远端能否直接推送 `main`，不能时明确报错"。实现做的是 `push --dry-run` 本地 `main`，结果是：
- 离线、认证失败、本地没有 `main`、本地落后远端时，init 都失败；
- dry-run 本身也证明不了真有推送权限。

这与 NFR-01（本地优先）和 FR-98（init 只生成文件）冲突。

- ★ A：降级为尽力检查。先 fetch，再拿 `origin/main` 的 SHA 做 dry-run 协商。只有明确的拒绝（例如受保护分支、权限不足）才报错；网络失败、认证失败、没有本地 `main` 都只给警告，说明"快照写入时会再次检查"。规格末句同步改为这个意思。
- B：保持硬失败，只修正检查基准，改用 `origin/main`。

### P0

#### R1 离线时命令照常可用

- **偏差**：每条命令都同步执行 `git fetch origin`，超时 30 秒，fetch 失败时整条命令失败。断网时 `status` 和续租都失败，15 分钟后租约过期，Agent 的工作白做。
- **依据**：NFR-01；FR-88 只要求领取、续租和主干租约连得上 hub，本地 hub 不依赖 git 远端；FR-83 只规定读 fetch 后的 `origin/main`，没说每次读之前都要 fetch。
- **证据**：`catalog.rs:45-57`；`daemon.rs:449`、`daemon.rs:528`。
- **整改**：
  - fetch 由守护进程在后台做：每个项目每 60 秒一次，同一时刻最多一次；写 `main` 之前（快照、重建）再同步 fetch 一次。
  - 读命令用最近一次 fetch 到的 `refs/remotes/origin/main`，不阻塞。
  - `status` 输出 `main.fetched_at` 和 `main.last_fetch_error`。
  - fetch 失败只发警告，不让读命令或续租失败。
- **失败测试**：
  - origin 指向一个不存在的路径时，`status`、`task show`、隐式续租都成功，输出里带 fetch 错误；
  - 10 个并发 `status` 只触发一次 fetch；
  - 断网期间租约不过期。
- **验收**：拔网 20 分钟，已领取的任务仍在运行，租约未过期。

#### R2 `init` 回到 FR-98

- **偏差**：
  1. 守护进程在运行时，`init` 会先续租，续租失败就中止 init。
  2. 推送预检被当作硬前置条件（见 D4）。
  3. 非交互调用时静默采用默认 docs_dir。
  4. 生成的 `.towermd/AGENTS.md` 里写着"快照尚未提供"等功能可用性说明，已经过时，而且已有的文件不会更新。
  5. 缺少 FR-105 要求的技能安装提示。
- **依据**：FR-98（init 在守护进程之前运行、要询问 docs_dir、Agent 的建议要经人确认）；FR-81；FR-105。
- **证据**：`main.rs:180-201`；`init.rs:110`、`init.rs:149-183`；`main.rs:269-277`；`templates/agents.md:7`；`init.rs:130-137`。
- **整改**：
  1. 把 `Command::Init` 从需要续租的命令列表中移除。
  2. 推送检查按 D4 的结论修改。
  3. 非交互、没有已有配置、又没传 `--docs-dir` 时报错："非交互模式须显式传 `--docs-dir`，请先与人确认目录"。
  4. 模板只写规矩，不写哪些功能已经可用，这样内容就稳定了，"已有文件与模板不同就警告"的策略可以保留。
  5. 加一条提示，说明技能包怎么安装。
- **失败测试**：

  - 非交互且不带 `--docs-dir` 时退出码为 1，并且没有生成任何文件；

#### R3 没有远端时也能写出快照（依赖 D1）

- **偏差**：见 D1。另外，推迟时不提示，后台每秒重试一次，每次都要重新加载目录、重放事件、列出工作树。
- **依据**：FR-89、FR-90、FR-91，NFR-02。
- **证据**：`snapshot_git.rs:71-78`；`daemon.rs:686-690`。
- **整改**：
  - D1 选 A 时：`main` 已检出就写 `refs/towermd/snapshot`；`main` 可写之后补写回 `main`；恢复和上任补发 ack 时，都在两处中取 `(epoch, seq)` 最大的那份。
  - 不论 D1 怎么选：
    - `status` 输出 `snapshot.last`、`snapshot.deferred_reason`、`snapshot.deferred_since`；
    - 推迟超过 `snapshot_interval` 时发 `alert.raised`；
    - 后台重试改为指数退避，上限为 `snapshot_interval`。
- **失败测试**：
  - 无远端、`main` 在主工作树检出时，`towermd snapshot` 写出快照，用户工作树和 index 的 `git status` 前后完全一致，`refs/heads/main` 不动；
  - 删除 hub 目录后能从这个引用恢复；
  - 推迟期间 tick 不再每秒做全量工作。
- **验收**：单人、无远端仓库能在快照间隔内落盘一次快照。

#### R4 hub 重建在产品路径上可达（依赖 D2）

- **偏差**：
  1. `AppConfirmation` 在 crate 外构造不出来，`execute` 只有测试在调用。
  2. 快照之后只要有带 `Towermd-` trailer 的提交，就拒绝恢复。FR-93 要求的是把它们补回成事件。任务合并时都会带 trailer，所以合并一次之后，重建就永远做不了。
  3. 发件箱没有接入恢复。
  4. hub 为空时所有命令都被拒绝，`status` 也不能用。
  5. `hub rebuild` 请求会隐式续租，请求本身也没有记录下来。
- **依据**：FR-93、FR-88、16.1、16.3，第 18 节 M0 验收。
- **证据**：`recovery.rs:24-28`、`recovery.rs:186-205`、`recovery.rs:326`；`snapshot_service.rs:333`；`daemon.rs:531`、`daemon.rs:614-648`。
- **整改**：
  1. 按 D2 的结论实现确认端点，加一个只供该端点使用的构造函数，可见性为 `pub(crate)`。
  2. trailer 回放：
     - 对已知的 trailer（`Towermd-Task`、`Towermd-Evidence`、`Towermd-Snapshot`，以及基线标签），按 FR-87 用"提交 SHA + 类型"生成确定的 `eid`，补回 `merge.done`、`snapshot.written`、`baseline.created` 等事件；
     - 遇到未知的 `Towermd-*` trailer，记一条 `alert.raised` 并附上原文，但不阻止恢复。
  3. 发件箱合并：
     - 按 `eid` 去重，`eid` 索引从归档的 jsonl 推导；
     - 带 `epoch` 的事件在重建后自然变成过期；
     - 发件箱里的续租事件直接丢弃。
  4. hub 为空时，`status` 能只读运行并报告"需恢复"，写命令仍然拒绝。
  5. `hub rebuild` 请求不续租，请求本身记到守护进程的运行时目录，供 App 读取。
- **失败测试**：
  - 删除 hub 目录后：请求重建，再以 App 客户端身份确认，`status` 恢复正常；旧 `epoch` 的写入被标为过期。
  - 快照之后有一次带 `Towermd-Task` trailer 的合并时，重建成功，并补回 `merge.done`，它的 `eid` 只由提交 SHA 决定。
  - 发件箱里有一条已经进入快照的事件，重放后只出现一次。
  - hub 为空时 `status` 退出码为 0，输出"需恢复"。
- **验收**：第 18 节的"删掉本地 hub 后能从快照重建，重建后旧 `epoch` 的写入被标为过期"，在端到端的守护进程测试中成立。

### P1

#### R5 hub 与快照的存储有界

- **偏差**：
  1. 每追加一条事件，都把整个 journal 重写一遍并 fsync。
  2. 收到 `snapshot.ack` 后也从不截断。
  3. 主干租约每 30 秒续一次，这些心跳的 `eid→seq` 全都写进 `state.json`，每天约 2880 条。
  4. 守护进程每秒全量重放一次所有事件，每条命令也要读全部归档再全量重放。
- **依据**：FR-87（截断后保留 `eid` 索引）、FR-89（心跳不归档）、FR-92（ack 之后可以丢弃事件内容）。
- **证据**：`hub.rs:621-712`、`hub.rs:481-501`；`snapshot.rs:128`；`snapshot_service.rs:193`、`snapshot_service.rs:319`、`snapshot_service.rs:413`；`daemon.rs:663`；`tasks.rs:442`。
- **整改**：
  1. journal 改为只追加：每条事件写一行并 fsync，不再重写整个文件。
  2. 收到 ack 后做压缩：把 `seq` 不大于 ack 的事件折叠成一个检查点（投影 + 非心跳事件的 `eid` 索引），丢弃这些事件的内容。正常运行时，以截断点之前的 `seq` 订阅，返回"请从快照加载"。
  3. `state.json` 不再存 receipts，只存省略心跳的 `seq` 区间，用区间表示；`eid` 索引在恢复时从归档的 jsonl 推导（D5）。
  4. 守护进程维护增量投影，只应用新到的事件；每条命令读的是内存中的投影。
- **失败测试**：
  - 追加 10,000 条事件后，journal 文件只增长新写入的那些行，inode 不变，没有被重写；
  - ack 之后 journal 变小，用已截断的 `eid` 重发仍然返回原来的 `seq`；
  - 续租 1,000 次以后，`state.json` 的大小与续租次数无关；
  - 守护进程跑 1 小时后，每次 tick 的耗时不随历史增长（用计数器断言重放的事件条数）。
- **验收**：长时间运行时，每次操作的开销是常数。

#### R6 hub 协议与事件对齐 16.3、6.3 节和 FR-86

- **偏差**：
  1. 租约变更附在 `append` 上一起提交，没有独立的租约操作。
  2. 租约被占用时只返回一个字符串错误，没有占用者信息。
  3. 从不产生 `lease.*` 和 `task.released` 事件。
  4. `task.claimed` 记成了 L4，而且这条事件的 `epoch` 是空的。
  5. hub 会解析 `data.commit`。
  6. 调用方直接依赖具体的 `Hub` 结构体，没有协议抽象，M2 接 Cloudflare hub 时要重写调用方。
- **依据**：16.3、6.3 节，FR-86，FR-99。
- **证据**：`hub.rs:197`、`hub.rs:285`、`hub.rs:587-637`、`hub.rs:762`；`tasks.rs:8`、`tasks.rs:496-509`、`tasks.rs:527`。
- **整改**：
  1. 定义 `HubProtocol` trait，覆盖 16.3 节的七个操作：`append`、`subscribe`、`lease_acquire`、`lease_renew`、`lease_release`、`snapshot_ack`、`rebuild`。本地 hub 实现这个 trait，`tasks` 和守护进程只依赖 trait。
  2. 租约操作由 hub 自己产生 `lease.granted`、`lease.renewed`、`lease.expired`、`lease.released` 事件，事件里带 `epoch`。占用时返回结构化的占用者信息。
  3. `task.claimed` 和 `task.released` 改为 L5；领取事件带上取得的 `epoch`；放弃和过期时产生 `task.released`。
  4. hub 只读事件信封。由 git 产生的事件，在调用方按"提交 SHA + 类型"算出确定的 `eid`，hub 只按 `eid` 去重。
  5. `claim` 的原子性：先取租约，再带 `epoch` 追加 `task.claimed`；追加失败就释放租约。
- **失败测试**：
  - 一套针对 trait 的契约测试，覆盖幂等、过期、占用、ack 和 rebuild。M2 的 Cloudflare hub 直接复用这套测试。
  - 领取、放弃、过期这三条路径各自产生的事件类型、层和 `epoch` 都对。
  - hub 代码不出现对 `data` 字段的访问（契约测试里塞一个畸形的 `data`，hub 照常定序）。
- **验收**：M2 的 Cloudflare hub 只需要实现这个 trait。

#### R7 快照写入的重做与连续前缀

- **偏差**：
  1. 推送被拒后，写入路径里不重新 fetch 重做，`towermd snapshot` 直接失败。
  2. 验证"快照点不越过连续前缀"的 `EventBuffer` 生产代码没用上，这条验收落在了一个没接入的组件上。
- **依据**：FR-91、FR-89，第 18 节。
- **证据**：`snapshot_git.rs:90`、`snapshot_git.rs:122`；测试 `competing_remote_push_is_rejected_without_retry`；`snapshot.rs:350`；`hub.rs:441`。
- **整改**：
  1. 推送非快进被拒时：重新 fetch，做 `(epoch, seq)` fencing 检查，在新的 `origin/main` 上重建提交，再推送；最多 3 次，之后报错。发现已有更新的快照时放弃写入，并记录原因。
  2. 在 `HubProtocol` 里提供 `contiguous_seq()`，快照点一律取它的值；删除 `EventBuffer`。本地 hub 自己发号，`seq` 天然连续；"先收到 103、后收到 102"这条验收改为在契约测试里，用一个乱序到达的测试替身验证，M2 再用 Cloudflare hub 实测。
- **失败测试**：
  - 并发推送一次后，`towermd snapshot` 自动重做并成功；
  - 另一个写入者已有更新的快照时，本次写入放弃，不推送。
- **验收**：旧的主干租约持有者醒来后写不进快照；正常的竞争推送不会让人看到失败。

#### R8 S5 改用 FR-107 的验证器（依赖 D3）

- **偏差**：
  1. 验证机制见 D3。
  2. 清空环境变量后，环境问题会被记成测试失败。
  3. 整批只产生一条证据，不是每个模块一条。
  4. 根目录的命令（`cwd="."`）会挂到所有模块上。
  5. 新增了规格里没有的 `baseline verify` 命令。
- **依据**：第 8 节 S5（输出每个模块的初始证据）；FR-107；16.1（`baseline scan` 覆盖 S1–S5）。
- **证据**：S5 工作树中的 `verifier.rs:66-121`、`verifier.rs:298-325`、`s5.rs:140-146`；`coldstart.rs:186-196`。
- **整改**（按 D3 选 A）：
  1. 实现一个验证器，S5 和 M1 的 `finish` 共用：
     - 在 `$(git-common-dir)/towermd/verify/` 下执行 `git worktree add --detach <sha>`；
     - 继承用户的环境变量，设超时，到时回收整个进程组；
     - 日志写到本机缓存，大文件按 FR-75 处理；
     - 证据由 `process:towermd-verifier` 署名，绑定 tree。
  2. 每个模块一条证据，结果为通过、失败或无测试。
  3. 命令和模块的对应关系：
     - 清单文件所在目录的命令，归到包含这个目录的模块；
     - 根目录的命令只给没有自己命令的模块用，证据里标明"共享"；
     - 同一条命令只跑一次。
  4. 把 `baseline verify` 并进 `baseline scan`：先异步返回扫描 ID，再用 `baseline scan --wait` 分段等待，每次最多 90 秒，与 `finish` 一致。
- **失败测试**：
  - 一个 Rust 加 JS 的夹具仓库：每个模块各得到一条证据；根目录的命令只跑一次；
  - 用户工作树里有未提交改动时，验证结果只反映所选提交；
  - 超时后整个进程组被回收；
  - CLI 里没有 `baseline verify`。
- **验收**：对 Tower.md 自己的仓库跑 `baseline scan --wait`，得到每个模块的初始证据，用户工作树不变。

#### R9 冷启动输出符合 S3 和 M0 交付物

- **偏差**：

#### R10 clone 锁不再永久绑定（FR-85）

- **偏差**：clone 的路径一旦写进 `project-<hash>.json`，就永久绑定。原 clone 删掉或仓库搬家后，这个项目在本机就用不了了。

- **证据**：`daemon.rs:141-158`；`daemon.rs:978-989`。
- **整改**：只有在记录的 clone 路径仍然存在、它的配置里是同一个项目 ID、而且 git 公共目录不同时才拒绝；其余情况改绑到新 clone，并记录这次改绑。
- **失败测试**：原 clone 删除后，新 clone 能启动；两个 clone 同时存在时，仍然拒绝。

#### R11 非法的 layer 值统一处理

- **偏差**：
  - `types::layer_of` 遇到非法的 `layer`，静默回退到默认层，例如 `Task` 的 `layer: L9` 被当作 L4；
  - `catalog` 遇到同样的情况则报错。
  - 同一个值，两处判定结果不一样。
- **依据**：FR-01、FR-17；原则冲突时，慢层保护优先。
- **证据**：`types.rs:111-121`；`catalog.rs:107-110`。
- **整改**：`layer_of` 返回三种结果：有效、缺失（用默认层）、非法。非法时，守卫按慢层处理，`catalog` 给出诊断，两处共用这一个函数。
- **失败测试**：`layer: L9` 的对象改动后，被路径守卫判为受保护路径。

#### R12 画布中的非法条目逐条处理（FR-100）

- **偏差**：几何字段以外，只要出现一个小数（比如未知键里的 0.5），整份画布就失去投影。
- **依据**：FR-100 要求非法条目作为不透明条目逐条保留，而不是整份不透明。
- **证据**：`canvas.rs:90-97`；`canvas.rs:466-473`。
- **整改**：整数检查只用于几何字段。未知键里的数字原样保留。几何字段非法的节点，只让这一个节点变成不透明条目。
- **失败测试**：未知键里有 `0.5` 的画布，投影出全部节点，往返后逐字节不变。

#### R13 任务状态与诊断的小偏差

  2. `claim` 接受"待定"状态的任务，直接跳到运行中，没有记录"待定 → 就绪"这一步。改为只能领取"就绪"的任务；"待定"的任务在 G0 通过后，先记一条 `task.state` 转成就绪。依据：10.2 节。证据：`tasks.rs:364`。

## 4. 整改完成的标准

第 18 节 M0 验收里的每一条，都必须在真实的守护进程路径上有对应的测试，不能只是测试夹具或没接入的组件。尤其是以下几条：

- [ ] 断网时命令可用，租约不过期（R1）
- [ ] 无远端、`main` 已检出时，快照在一个间隔内落盘（R3）
- [ ] 删掉本地 hub 后，经确认端点重建成功，旧 `epoch` 的写入被标为过期（R4）
- [ ] 快照点不越过连续前缀（R7，契约测试）
- [ ] 冷启动生成草稿 `tower.canvas`，每层模块数在 3–9 之间，每个模块都有初始证据（R8、R9）
- [ ] 长时间运行时，每次操作的开销是常数（R5）
- [ ] `init` 不依赖网络和守护进程（R2）
